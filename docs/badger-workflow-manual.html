SECTION 01

Terminology: four planes and the system vocabulary

Start with four planes, then learn the terms that connect them: human-readable instructions, a declarative contract, a durable runtime/control plane, and evidence that proves what happened. This order turns a long glossary into a map for every architecture diagram that follows.

How to use this section. Read left to right: capability → contract → execution → proof. For each term, ask what it describes, who owns it, what identity or artifact crosses the boundary, and whether the behavior is current or still a roadmap target. Then reuse the interview sentence at the end.
1. Instruction planeSkills, references, scripts, Creator, and Factory describe capability.
2. Contract planeProtocol, Nodes, schemas, guards, and routes declare meaning.
3. Runtime/control planeEngine, Run, actions, revisions, and recovery own execution.
4. Evidence planeIdentity, artifacts, trajectory, review, and readiness prove claims.

Instruction and composition concepts

Skill
A versionable capability package, usually centered on Markdown instructions and optionally references, scripts, runtime metadata, guardrails, and evals. A Skill describes how an agent or external executor should perform a bounded capability.
Skill Harness
The surrounding control system that discovers Skills, composes them into a workflow contract, runs them through a durable runtime, records evidence, and exposes safe lifecycle operations. It is broader than a Skill itself.
Badger
The focused standalone package in this repository. It provides a certified Engine foundation and the WorkflowRuntime seam that turns workflow-kernel contracts into executable Runs.
Creator
The user-facing authoring façade that turns a goal, selected Skills, and confirmed choices into a persisted factory plan, an authoring plan, and a generated package. It authors the package; it does not run the package’s individual WorkflowRuntime Runs.
Factory
The controlled package-production lifecycle around proposal, confirmation, composition, authoring, deterministic assembly, evaluation, review, publication, and distribution. It is a supply chain for workflow packages, not a single prompt call.
Generated package
The deterministic directory emitted from a validated WorkflowProtocol and reviewed authored content. Its Auto zone supplies control-plane structure; its Authored zone supplies domain judgment that automation cannot infer.
Workflow-kernel
The package kind used for a generated workflow whose Nodes, transitions, outputs, guardrails, and recovery model form its control plane. It is not merely a folder of prompts.

Contract and control concepts

Workflow Protocol
The declarative, normalized contract for one executable workflow. It describes Nodes, Skill bindings, Output Schemas, transitions, routing fields, decision definitions, cycle policy, artifact lifetimes, and evaluation expectations. It is distinct from the Authoring Protocol that governs package construction.
Authoring Protocol
The declarative contract for constructing a workflow package. It defines authoring lanes, dependencies, claims, authored content leaves, deterministic backbone artifacts, review depth, and the boundary between worker drafts and final assembly.
Node
A named unit in the Workflow Protocol. An action Node invokes a Skill or executor; a control Node chooses a route; a decision Node waits for an authorized human response; a handoff Node summarizes a boundary.
Binding
A declaration connecting a Node to a Skill, operation, scope, and enforcement mode. Bindings let one workflow use several independent Skills while keeping the composition explicit.
Output Schema
A completion contract for a Node. It names required artifacts and evidence fields, so “the agent says it is done” is not sufficient by itself.
Guardrail
A predicate or policy check that permits, rejects, or blocks an action or transition. It validates prerequisites; it is distinct from the interaction that obtains a human decision.
Handoff
A structured transfer or summary at a workflow boundary. It should expose the current continuation, relevant metadata, evidence, warnings, and an exact resume target rather than relying on conversation memory.
Action
A runtime instruction such as invoke_skill, call_tool, ask_user, handoff, or checkpoint. The pending action is the durable unit the host is asked to perform or answer.
Transition
A declared move from one Node to another after an outcome. A transition may be unconditional, conditional, a decision-choice mapping, a repeat transition, or a terminal edge.
Route condition
A constrained predicate over submitted routing values, such as scenario=pool-only. The resolver accepts only declared fields and values and rejects ambiguity rather than evaluating arbitrary code.

Runtime concepts

Engine
The generic execution substrate retained from the upstream reference. It manages Run state, pending actions, deterministic or adaptive resolution, outcomes, retries, trajectories, checkpoints, guardrails, and manual or standalone persistence.
WorkflowRuntime
The deep module that interprets a Workflow Protocol for one durable Run. It compiles Nodes into Engine actions, resolves transitions, validates completion, manages decisions and cycles, and projects a structured continuation.
Run
One durable execution instance. Its state includes identity, status, current action, revision, retry context, cycle and visit ledgers, artifacts, and evidence. A Run survives the process that created it.
Run location
The storage adapter for a Run. A manual location uses a caller-supplied directory; a standalone location maps a validated Run id to <project>/.badger/runs/<runId>. Both use the same runtime semantics.
Pending action
The persisted action proposed by the runtime and awaiting an outcome or decision. It gives the host an exact identity to execute or answer, which makes interruption and replay checks possible.
Continuation
A structured projection of what can happen next: continue, await-user, blocked, or done, together with the current Node, pending action, blockers, identity, and ledgers.
Resolver
The deterministic policy that selects the next Engine step from the current step, Run state, and submitted outcome. The generic WorkflowRuntime resolver understands declared transitions, exact predicates, fallback behavior, and cycle allocation.
Compiler
The transformation from normalized Workflow Protocol to an Engine-compatible Skill package: action steps, Node-to-step mapping, runtime metadata, completion plans, guardrails, and an execution identity.
Deterministic and adaptive modes
Deterministic mode follows declared resolution rules; adaptive mode can select among allowed candidates under guardrails. The private WorkflowRuntime target keeps workflow routing deterministic even when work inside a Node is agentic.
Operator-driven execution
A control split in which the runtime decides and records what is admissible while a human, Agent, script, or installed runtime performs the external work and submits the result. It is a mode of control, not a third Run format.
Revision
A monotonic logical version of a Run. It starts at zero and advances once for each accepted outcome or decision response. Stale submissions must fail without mutation.
Attempt
One visit to a Node within a Run and Cycle. Engine retries remain inside the same Attempt; a declared re-entry creates a new Attempt so repeated work and evidence do not overwrite each other.
Cycle
A declared, bounded repetition of a workflow region. A Cycle has a stable key, instance ordinal, identity, entry Node, repeat transitions, and a finite budget.
Projection
A rebuildable compatibility view, such as generated workflow-state.mjs output. It helps operators and legacy commands, but it is not the routing, recovery, eval, or readiness authority.
Side effect
A change outside the runtime’s own logical record, such as writing an artifact, downloading a genome, submitting a scheduler job, or replacing a package. Side effects require explicit contract boundaries and evidence.
Transition journal
An append-only or write-ahead record of the previous and intended next state used to reconcile interruption at a mutation boundary. It is a Badger durability mechanism, not a platform or domain workflow policy.
Mutation lock
A per-Run coordination mechanism that permits one mutating operation at a time and makes stale-lock recovery explicit. It prevents concurrent submissions from both advancing the same revision.

Evidence and delivery concepts

Execution identity
The binding between normalized protocol hash, compiled package hash, immutable Skill snapshot hash, and deterministic Node-to-Engine-step mapping. Revisioned workflows also bind capability and resolver identities.
Skill snapshot
An immutable, content-addressed capture of the executable Skill definition and declared scripts. It lets a Run prove which Skill version it actually used.
Trajectory
An append-only event history of a Run. It records proposals, outcomes, checkpoints, migrations, state transitions, evals, and recovery reconciliation instead of treating mutable status as history.
Checkpoint
A durable recovery boundary associated with state version, trajectory offset, context hash, artifact hash, and creation time. It is evidence about a stable point, not a replacement for the Run state.
Decision Receipt
An identity-bound record of an accepted human choice. It includes Run revision, action, Node, Cycle, Attempt, reviewer authority, selected choice, and relevant evidence or artifact scope.
Artifact version
An immutable, content-bound record for a declared output. Its lifetime may be Attempt, Cycle, or Run; later work selects an exact accepted version instead of resolving an ambiguous “latest” file.
Artifact
A declared file or directory produced or consumed by a Node. A declared artifact has an expected kind, bounded path pattern, validation rules, and possibly a version lifetime.
Provenance
The identity trail connecting an outcome or artifact to its producer Node, Run, Cycle, Attempt, action, input or package hash, and runtime time. Provenance answers “where did this result come from?”
Evidence scope
The bounded set of accepted artifact and append-only evidence references that a decision or verification covers. A changed scope makes the old response stale.
Certification
A repeatable evidence gate that checks behavior across a defined matrix. Engine certification establishes official/private parity; WorkflowRuntime certification establishes identity, lifecycle, adapter, recovery, and negative-case coherence.
Readiness
A current-hash judgment with separate authoring, runtime, and publication dimensions. A package needs complete authored content, valid runtime evidence, and the required approval; file presence alone does not make it ready.
Generated runtime
A bundled delivery artifact produced from explicit source entries and authored content. It carries reviewed behavior into a Skill; it must remain a projection of source and contract, not a second place to author policy.
Current-hash evidence
Evidence computed for the exact package, protocol, snapshot, or fixture identity being judged. If the material changes, the prior evidence is stale until rerun.
Idempotency
The property that retrying a bounded operation does not create an unintended second effect. It is especially important when external work and runtime submission can be separated by a crash.
Authorization
A check that the actor, reviewer, or operation is allowed to perform the requested transition. A validly shaped response is not automatically an authorized response.
Observability
The ability to explain and inspect execution through structured state, events, hashes, findings, receipts, and diagnostics rather than inferring behavior from a final message alone.
Repair policy
A bounded rule for deciding whether a failed or blocked Run may retry, repair, pause for a decision, or stop. It prevents repeated failure from becoming an unbounded silent loop.
Transactional finalization
A preview–confirm–mutate–reconcile sequence for high-consequence completion or publication. Preview is evidence about a proposed change, not proof that the change was applied.

“I explain the system as four cooperating planes. Skills and Creator form the instruction plane; Workflow Protocol forms the semantic contract plane; WorkflowRuntime plus Engine form the runtime/control plane; and identities, artifacts, trajectories, receipts, evaluations, and readiness form the evidence plane. The planes have different owners, so an Agent can contribute work without becoming the authority for routing or durable state.”

2.1 The top-level target

The target has one portable instruction-and-contract input, an integrated authoring plane, one reusable runtime authority, multiple future host adapters, and a separate evidence path. The critical handoff is an assembled package and Skill snapshot plus execution identity: Authoring constructs the package, WorkflowRuntime executes a Run, and neither reinterprets the other’s state.

Three boundaries to keep visible

Authoring boundary

Creator/Factory resolves sources, confirms the WorkflowProtocol, runs the Authoring Protocol, validates lane evidence, and assembles the reviewed package. It owns package meaning, not the state of each Run.

Execution boundary

WorkflowRuntime consumes the immutable snapshot and proposes or accepts pending actions. A human, Agent, script, or tool performs external work; only Runtime mutates the Run.

Evidence boundary

The evidence ledger ties package, Run, artifacts, decisions, trajectories, evaluations, and readiness together. Delivery gates inspect that record rather than a final message.

instruction/sourcecontract and packageexecutionevidence and delivery

How to read the flow

Follow the solid path from the goal and source Skills to a normalized Workflow Protocol, an Authoring Plan and lane outputs, an assembled package, an immutable snapshot, and WorkflowRuntime/Engine. The host receives a continuation, performs one proposed action, and submits an outcome; it does not choose an arbitrary next Node.

Follow the parallel evidence path separately. It records identity, artifacts, receipts, trajectory, evaluations, and readiness, then supports preview, approval, publication, and distribution. “The Run completed” and “the package is ready” therefore remain separate claims with separate evidence.

“At the highest level, Badger is a governed package factory plus a durable execution product. Creator/Factory owns meaning and delivery evidence; WorkflowRuntime owns each Run; the host performs external work. The immutable package snapshot and execution identity are the handoff. Only the runtime can accept an outcome and move the Run, while evidence connects that execution to evaluation, readiness, approval, and delivery.”

2.2 The abstraction ladder

The same architecture becomes easier to remember when viewed at progressively lower levels. This is a zoom model, not a second lifecycle: each level answers a different question while preserving the same package identity, runtime authority, and evidence boundary.

Read the ladder as zoom, not sequence

Level 1 · EcosystemWho participates, and where evidence goes.
Level 2 · PackageWhat is declared before execution.
Level 3 · RunWhat one Run persists.
Level 4 · TransitionWhat happens between two states.
Level 5 · Files and modulesWhere boundaries live in code.

The invariant to remember

At Level 1, the story is a governed workflow ecosystem; at Level 2, a declarative package; at Level 3, a durable Run; at Level 4, a guarded prepare–execute–submit–validate–resolve turn; and at Level 5, the concrete module seams that implement those meanings.

The zoom changes vocabulary, not authority. Every view points back to the same package identity, pending action, validation boundary, and continuation. A generated Markdown file is an instruction surface; the module that owns state, transitions, validation, and recovery is the runtime.

“I explain the five levels as zoom, not as five different systems. Ecosystem asks who participates; package asks what is declared; Run asks what is persisted; transition asks how one turn is guarded; and module asks where the boundary lives in code. The vocabulary changes at each zoom, but package identity, pending action, validation, continuation, and one runtime authority remain invariant.”

2.3 WorkflowRuntime inside the codebase

Current seam The private package exposes one public constructor and four operations—start, resume, submit, and recover. That small surface is the stable contract; Engine state, validation, routing, artifacts, storage, and durability evolve behind it.

Public contract, private machinery

How the seam divides responsibility

Caller contract

Callers provide a normalized protocol and Run location, then receive a structured continuation. They do not coordinate compiler state, storage files, locks, checkpoints, or route selection themselves.

Private capability set

Compiler, resolver, completion checks, decision scope, artifact versions, Run locations, protected storage, durability records, and generated projections remain implementation details behind WorkflowRuntime.

The compiler turns the protocol into Engine actions and binds execution identity. Location adapters normalize manual and standalone persistence. Completion validates Output Schemas, required Skill calls, augmentations, guardrails, and artifacts; routing selects declared transitions and allocates Cycle/Attempt state; decision and artifact modules reject stale scope before mutation.

The current Badger implementation already provides protected state, revision fences, transition journals, mutation locks, verified checkpoints, structured findings, verification receipts, content snapshots, repair policy, and transactional finalization. The authoring upgrade adds package-construction evidence around that runtime; it does not import Classic or Native phase policy.

Authority rule. Generated workflow-state.mjs, workflow-guard.mjs, and workflow-handoff.mjs are adapters and projections. They may read or request a runtime operation, but they must not create a second next-Node algorithm or become the source of recovery truth.

“The key module decision is one runtime authority. Callers see start, resume, submit, and recover; private capabilities compile, route, validate, persist, and project behind that seam. Generated scripts preserve compatibility but delegate to WorkflowRuntime, so no second state machine can drift from the Engine-backed Run.”

2.4 Primer Designer as a workflow instance

Future domain project Primer Designer is a planned generic workflow instance, not the definition of the runtime. Its three source Skills remain independent—genome-download, primer-design, and primer-pool-add—and migration follows runtime and authoring proof. This section describes contract shape; it does not claim biological execution or a publishable package.

Read the domain graph in four passes

Prepare and resolve inputs

Establish scenario, sources, parameters, workspace, executor, and resume identity before any domain side effect.

Produce design evidence

Run the declared reference, outgroup, coverage, extraction, selection, Primer3, and quality-control Nodes; optional genome acquisition and USEARCH remain explicit branches.

Build and filter the pool

Enter the pool path at p0 and apply compatibility and filtering Nodes through p10, preserving output schemas and artifact versions.

Handoff and decide whether to repeat

Reconcile warnings, provenance, and species status, then use a declared choice for finish, pool-add, or another bounded Cycle.

The contract describes 26 Nodes and several explicit route variants, but the architecture is the separation of concerns. Input preparation establishes identity before side effects; scenario routing selects pool-only or design paths; design Nodes produce progressively stronger sequence and primer evidence; pool Nodes apply compatibility and filtering; the handoff reconciles artifacts, warnings, provenance, and the exact next-cycle choice.

After the runtime target is proven, every review that changes scope, acceptance, risk, or whether another cycle begins should be a first-class decision. A repeated design cycle receives a new Cycle and Attempts, preserves prior artifact versions, and records parameter overrides. The generic runtime enforces these invariants; the Primer Designer contract supplies the biological meaning.

Generic runtime versus domain contract

Generic runtime responsibility

Persist pending actions, validate revision and action identity, enforce schemas and guardrails, select legal transitions, allocate Cycle/Attempt state, bind artifact provenance, and expose recovery. It does not define biological validity.

Primer Designer responsibility

Define valid genome, design, and pool outputs; species status and unresolved species; review choices; parameter overrides; and the scientific acceptance policy for finish or repeat.

“Primer Designer is a domain contract over the generic runtime. It keeps genome-download, primer-design, and primer-pool-add independent, then declares the Nodes, schemas, routes, review choices, and Cycle policy that compose them. WorkflowRuntime supplies identity, persistence, validation, routing, and recovery; the domain contract supplies the biological meaning and acceptance criteria.”

2.5 Why this design fits Skill Harness

The design occupies a deliberate middle layer. A Markdown Skill is excellent at expressing a portable method, but its guarantees depend on the current Agent, context, and operator. A full Agent runtime is excellent at open-ended planning and delegation, but its wider autonomy brings a larger policy, security, and observability surface. Skill Harness is for the case between them: the route, acceptance boundaries, and evidence obligations are knowable in advance, while the work inside a Node may remain probabilistic, tool-driven, or human-led.

Decision rule. Choose a Skill Harness workflow when (1) legal Nodes and decision points can be declared, (2) execution may leave the process or use an Agent, and (3) accepted outputs must survive interruption, remain attributable, and be reviewable. Use a plain Skill when those guarantees are unnecessary; use a broader Agent runtime when the route itself must be invented at runtime. This is a fit test, not a maturity ranking.

Why the middle exists

Markdown Skill

Best for portable method, references, and progressive disclosure. It is cheap to author and move, but it does not define a canonical pending action, acceptance record, or recovery identity.

Skill Harness workflow

Best when the control boundary is explicit. It adds a typed protocol, one runtime authority, durable evidence, and bounded recovery while leaving Node-level reasoning flexible.

Full Agent runtime

Best when planning, delegation, and adaptation are themselves the problem. It can explore broadly, but requires wider controls for policy, security, cost, and replay.

How selective determinism works

Declare the boundary

The Workflow Protocol names Nodes, bindings, action types, schemas, guardrails, routes, decisions, and cycle limits.

Propose one action

WorkflowRuntime snapshots the package, binds execution identity, persists the pending action, and returns a structured continuation.

Perform outside the state machine

A human, Agent, script, or tool performs the proposed work and returns artifacts and evidence; it cannot mutate Run state directly.

Accept or stop

WorkflowRuntime checks revision and action identity, schemas, guardrails, authorization, and artifact scope, then advances once or returns await-user/blocked without mutation.

Selective determinism fixes what must be stable—identity, legal transitions, acceptance, and evidence—without pretending to control model reasoning or external-service behavior. That is the reusable seam: probability is allowed inside a declared Node; authority remains at the runtime boundary. Once Primer Designer is migrated, a QC handoff could offer typed choices such as finish, pool-add, or another-cycle; an Agent may inspect the evidence, but it cannot skip to p0 or overwrite an earlier artifact.

Position is a choice, not a maturity ladder

What the harness guarantees—and what it does not

Inside the runtime boundary

  • Current foundation One WorkflowRuntime authority, hash-bound Run identity, explicit pending actions, schema and guard checks, immutable artifact versions, and fresh-process recovery.
  • Delivered hardening Protected state, revision fences, journals, locks, verified checkpoints, receipts, snapshots, repair policy, and transactional finalization.

Outside the runtime boundary

  • The runtime does not make model reasoning or scientific validity deterministic; domain contracts and review still define meaning.
  • It does not replace host authorization, external-service reliability, or safe biological operations.
  • A preview, trace, or generated file is not by itself proof that publication or execution was applied.

Research context and practical trade-off

Research context. Adjacent systems increasingly study durable graph execution, checkpoints, interrupts, event histories, tool guardrails, sessions, structured handoffs, and evaluation harnesses. Skill Harness borrows that problem decomposition, not an implementation identity: an Agent is an external probabilistic worker inside a deterministic protocol, and interruption, evidence, and replay are explicit design objects.

Industrial implication. The same boundary supports bounded side effects, idempotency, authorization, stale-command rejection, audit trails, package provenance, observability, and recovery after process failure. The authoring target adds provenance for semantic content and lane review, while the delivered Runtime remains responsible for execution durability and does not import Native-specific phase policy.

Trade-off. The Harness gives up some open-ended autonomy and raw Markdown minimalism to gain explainability, testability, and controlled recovery. It is the right fit when steps and acceptance boundaries are knowable, but the reasoning and execution inside each step may still be agentic or tool-driven. It is the wrong fit when either a simple instruction is enough or the route must be discovered without a declared contract.

“I position Skill Harness by the control boundary, not by a maturity ladder. Use it when the legal route, acceptance evidence, and recovery identity can be declared, while the work inside a Node may remain agentic. The protocol names the allowed graph; WorkflowRuntime proposes and accepts actions; an external worker performs them. That buys explicit decisions, immutable provenance, and fresh-process recovery at the cost of some autonomy and authoring simplicity. Primer Designer is a good fit because its cycles and review boundaries are knowable even though its scientific work remains external.”

SECTION 03

Lifecycle: authoring, package, and Run recovery

There are three related lifecycles joined by one immutable boundary. The Authoring Protocol constructs semantic content and review evidence; the Factory assembles and evaluates a package; WorkflowRuntime creates and advances one durable Run from that package. Keeping these clocks separate explains what is ready to distribute, what is waiting to execute, and what can be recovered.

Keep authoring, package, and Run lifecycles separate. A scaffold may exist before authored content is complete; an assembled package must pass deterministic evaluation before publication; and a Run can finish without making the package publishable. Authoring owns content and lane evidence, the Factory owns package assembly and delivery evidence, and WorkflowRuntime owns each Run’s state transition. The handoff is an assembled package snapshot plus execution identity, not copied conversation context.

3.1 Build and release the package

Discover and resolve Skills

Resolve concrete source entries, preserve provenance, hash content, and surface missing or ambiguous candidates instead of silently substituting.

Confirm the Workflow Protocol

Normalize Nodes, bindings, schemas, guardrails, routes, decisions, cycles, artifact lifetimes, and evaluation expectations; persist explicit proposal confirmation before generation.

Author the semantic content

Derive the six-lane Authoring Plan, dispatch independent script/reference/pause-point work, then author the entry Decision Core and Node Guidance after their dependencies are satisfied. A scaffold with AUTHORING PENDING markers is not a usable package.

Assemble, evaluate, and gate delivery

Merge validated content leaves onto the deterministic Auto zone, render reference evidence, run current-hash runtime evaluation, inspect authoring review findings, and require publication approval before copying or previewing delivery.

3.2 Execute one Run

Start a Run

start validates the protocol and location, compiles or loads Engine state, snapshots the package and Skill, binds execution identity, and persists revision 0 with the first pending action.

Perform the pending action

The host reads the continuation; a human, Agent, script, or external executor performs the proposed work and returns artifacts and evidence. The external actor does not advance Run state directly.

Submit and validate

submit carries the Run, action, revision, and outcome identity. Runtime checks schemas, required calls, guardrails, and artifact/evidence scope before mutation; invalid or stale submissions leave committed state unchanged.

Resolve the disposition

An accepted outcome appends evidence, advances revision once, and lets the resolver choose the next Node, Cycle, or Attempt. The caller receives continue, await-user, blocked, or done.

3.3 The four public operations

start

Current seam Create a new Run at a validated manual or standalone location, compile the protocol, snapshot the package, bind execution identity, and persist the first pending action.

resume

Current seam Read committed Run state and return its current continuation. Do not replay the last action or rebuild intent from a conversation; if a recovery boundary is pending, settle it first.

submit

Current seam Accept one machine outcome or typed decision response. Check action, revision, execution identity, schemas, guards, and artifact scope before a single state advance.

recover

Current seam When a durability journal, lock, or checkpoint is pending, explicitly reconcile protected records and return the same continuation or a structured blocker. External work is never replayed implicitly.

3.4 Decision and recovery branches

Decision Nodes use the same turn but replace a machine action with a persisted ask_user action and an await-user continuation. The host presents the stable question and choices; only submit can accept the response. The response must match revision, action, Node, Cycle, Attempt, package identity, choice, reviewer policy, input schema, rationale policy, and required evidence scope. An accepted choice creates one identity-bound receipt and follows only its declared transition; invalid, stale, replayed, or cross-kind responses do not mutate the Run.

Recovery is an explicit branch, not a conversational restart. recover reads protected Run state, pending action, Skill snapshot, execution identity, ledgers, artifacts, and any journal, lock, or checkpoint record. Known interrupted writes can roll forward deterministically; unknown identity remains blocked. Recovery returns a continuation after reconciliation, and never silently repeats the external action.

“A Run is an exchange between a deterministic runtime and an external executor. The runtime proposes one pending action, the executor performs it, and the host submits a result. Completion validation and identity checks happen before the Run mutates. If the process stops, a new process reads the persisted state and reconstructs the same continuation. For a decision Node, the pending action becomes an authorized waiting state rather than an informal instruction.”

SECTION 04

Codebase guide: learn Badger as a standalone system

This section changes viewpoint: stop reading the package as a roadmap and read it as a small TypeScript product you could have designed. Start with the user-visible command path, then inspect the data contracts, module seams, durable files, and evidence gates that make each step trustworthy.

Scope and reading rule. Treat @rpamis/badger as a standalone design. It is an ESM Node >=22 library and CLI; its source of truth is under src/, its generated runtime assets are projections under assets/runtime/, Creator state lives under .badger/, authoring sessions live under .badger/authoring/, and a WorkflowRuntime Run stores its own records under .badger/runs/. Follow exports and persisted identities rather than inferring authority from a filename.

The Agent starts with badger guide. On a project with no existing FactoryPlan or resumable Creator flow, `/badger-create` automatically starts the multi-exchange questionnaire. Existing plans and authoring sessions are preserved; refinement requires an explicit questionnaire invocation.

An upgrade plan additionally supplies sourceRoot, and that directory must also appear in skillSources. Node implementations, Required Skill Calls, augmentations, schemas, guardrails, decisions, routes, and recovery behavior are completed from the conversation; the CLI validates and normalizes them without inventing missing semantics.

FactoryPlan relationships

  • Implementation binding identifies the supplied Skill that owns a Node.
  • Required Skill Call requires another supplied Skill inside a Node without replacing its implementation.
  • Augmentation assists a Node without replacing its implementation.
  • Output Schema declares the artifacts and evidence produced by a concrete Node.
  • Guardrail controls advancement using declared validation or evidence.
  • Decision Node exposes stable user choices and declared transition targets.
  • Handoff returns bounded evidence to another Node, reviewer, or user.
  • Routing transitions connect success, failure, pause, conditional outcomes, and completion.
  • Cycle declares bounded repeat transitions and continuation semantics.

FactoryPlan completeness checklist

Before proposal handoff, the questionnaire confirms goal and intent, explicit source paths and roles, inputs, Node responsibilities, Required Skill Calls, augmentations, decisions, Output Schemas, artifacts, evidence, guardrails, routes, optionality, failure, pause and recovery, handoffs, executable disclosures, upgrade-source behavior, locale, capabilities, finalization, and all unresolved assumptions. It continues exchanges until this checklist passes or the user explicitly stops with the remaining gaps recorded.

The questionnaire handoff labels confirmed user facts, source-derived facts, Agent inferences, unresolved assumptions, and remaining questions. A complete plan is shown and confirmed before read-only proposal generation; proposal confirmation remains separate from badger init --confirm.

4.1 The user-to-code path

The first useful narrative is the safe factory journey. A user begins with a goal and a plan, inspects what the project can resolve, previews a normalized protocol, confirms the write, creates a deterministic scaffold, completes the authoring lanes, assembles the package, evaluates its current hash, obtains separate authoring and publication review evidence, and only then publishes or previews distribution. The same package can subsequently be used by the generated adapters or the public WorkflowRuntime API to create a durable Run.

Inspect context

guide reports resumable Creator state; candidates resolves only explicitly declared Skill locations and returns descriptions, references, scripts, and content hashes.

Preview meaning

propose loads the plan, normalizes the Workflow Protocol, and reports candidates, blockers, warnings, and the plan hash without creating Creator state.

Confirm the draft

init --confirm is the explicit write gate. It persists a hash-bound CreatorState with status draft and creates the draft directory.

Scaffold and author

generate creates the deterministic control-plane scaffold; the authoring-plan, lane handoffs, and authoring-record flow supply the semantic content and review evidence. A scaffold is not a ready package.

Assemble and evaluate

The assemble step stages a deterministic scaffold, merges validated Authored zones with the Auto zone, and swaps the complete package into place; eval then hashes that exact package and records route, entry, manifest, and WorkflowRuntime certification checks.

Review and approve

review reports authoring, runtime, and publication readiness. A publication reviewer must explicitly approve the same current hash with approve --reviewer <id> --confirm.

Publish or preview

publish --confirm copies only an approved current-hash package into .badger/published/; distribute reports destination files and remains preview-only.

GateWhat it protectsWhat to say in an interview
Read-only discoveryCandidate resolution and proposal inspection do not create a workflow or copy a package.“The system lets me inspect meaning before it mutates state.”
Explicit confirmationInitialization, approval, publication, and report output require an intentional flag at the boundary that writes.“Confirmation is attached to the consequential operation, not hidden in a previous prompt.”

4.2 Use the tool as a user

Invoke assets/skills/badger-create/SKILL.md in an Agent after building the package. The Agent supplies each Skill by name and location, and the CLI inspects only those explicit sources. 4.3 Choose parameters and read their meaning

Choose parameters in three passes. First define the workflow’s meaning in the plan and the package’s authoring profile; then choose the safety and identity controls for the command; finally bind a runtime call to one project/Run location and one pending action. Defaults are useful for a small linear example, but optional routing, decisions, cycles, artifact versions, durability, and authoring review depth should be chosen only when the domain needs their extra proof.

4.4 Package architecture: modules and seams

Read the source from the outside inward. The CLI is intentionally thin. The workflow-kernel foundation coordinates discovery, normalization, proposal, and Creator state. The integrated authoring subsystem coordinates lane plans, worker evidence, authored content, and authoring review. The factory emits a package through one deterministic assembly boundary. Skill Runtime turns package files into a validated in-memory SkillPackage and an immutable snapshot. Engine supplies generic Run mechanics. WorkflowRuntime is the deep module that joins the protocol to Engine behavior and hides protected persistence. The package root and the /engine, /workflow-runtime, /skill-runtime, and /cli subpaths are public; protected storage helpers remain private. Evaluation, publication, differential harnesses, and tests consume those seams rather than creating a second authority.

How to read it. Follow the solid arrows from the thin CLI into the contract, authoring, and factory layers, then notice the two downstream paths: the assembled package becomes executable through Skill Runtime and Engine, while the public WorkflowRuntime export leads to the single runtime authority. The dashed arrows are verification relationships; tests and differential observations inspect those authorities without becoming a second implementation.

Illustration. A user command first reaches src/cli.ts, which delegates discovery and normalization to workflow-kernel. The authoring subsystem then validates lane outputs and content leaves; the factory assembles one package that Skill Runtime can validate and Engine can run. Evaluation and differential checks can refuse readiness, but they do not route a Run. That dependency direction keeps authoring policy, execution policy, and evidence from competing for ownership.

Factory and contract modules

How to read it. The plan and discovered Skills arrive from separate inputs, then meet at buildProposal. That proposal is the boundary between understanding and mutation: it makes normalized meaning, candidate identity, warnings, blockers, and the plan hash visible before init --confirm creates state. Generation creates the deterministic scaffold; the authoring lanes then provide content leaves and review evidence; assembly writes the final package.

Illustration. Suppose a plan requests the primer-design Skill. Discovery records its root and source hash while normalizeWorkflow checks its Nodes, schemas, routes, and guardrails. If two roots match, the proposal carries an ambiguity blocker, and initialization stops. After the candidate is resolved and confirmed, .badger/states/<name>.json records the Creator draft and .badger/authoring/<name>/ records lane evidence. The assembler produces SKILL.md, protocol metadata, Node Skills, references, and scripts without allowing authored content to become a second runtime authority.

workflow-kernel/discovery.ts

Searches project and global roots, reads SKILL.md descriptions, inventories references and scripts, hashes the source tree, and reports available, missing, or ambiguous candidates under a strict policy.

workflow-kernel/hash.ts

Produces stable fingerprints over sorted regular files and supported links so source evidence can be compared without relying on directory order.

workflow/contract.ts

Validates Node responsibilities, bindings, schemas, decision definitions, routes, and cycles; then normalizes defaults, edges, capabilities, state shape, and evaluation metadata.

workflow-kernel/foundation.ts

Owns the shared plan/proposal/state flow. The standalone adapter fixes the namespace to .badger while preserving the contract semantics.

authoring/* + factory/*

The authoring modules validate lane plans, records, claims, content leaves, and review; factory modules retain proposal, state, scaffold, and deterministic assembly responsibilities. Neither authored prose nor generated adapters becomes a runtime authority.

src/cli.ts

Maps command-line arguments to those seams and emits JSON or formatted values. It should remain orchestration glue, not a second implementation of normalization or lifecycle policy.

Skill Runtime, WorkflowRuntime, Engine, and storage

How to read it. Every public operation enters one Core, which fans out to focused policies and adapters before the results converge into one WorkflowContinuation. Identity is carried into the decision; location selects manual or standalone coordinates without changing Engine semantics; storage preserves state, pending work, trajectory, artifacts, and protected writes. The diagram is therefore a responsibility map, not a collection of independent routers.

Illustration. On start, the compiler turns the protocol into an Engine-compatible package, binds its package and snapshot identity, and persists the first pending action. A host performs that action and calls submit with the current actionId and revision. Completion checks schemas and guardrails, routing selects the legal next Node or Cycle, and the caller receives continue, await-user, blocked, or done. If the process exits, resume or recover reads the stored records; a generated adapter cannot bypass that authority.

Evidence, evaluation, publication, and differential modules

How to read it. Start with the assembled package and follow two evidence gates: authoring readiness checks content leaves, lane claims, and authoring review; deterministic evaluation binds the resulting tree to a hash and runtime certification checks its declared behavior. Differential observations compare the implementation with the pinned baseline. These results feed reviewState and readiness. Approval and publication are gated writes, while distribution is deliberately only a preview.

Illustration. Imagine package hash H1 has complete authoring evidence, passes runtime evaluation and certification, and receives publication approval. Publication may then copy exactly H1 into the published area. If an authored or generated file changes, the package becomes H2; the old authoring review, evaluation, and publication approval no longer prove readiness, so the affected evidence must run again. A failed parity or negative-case check keeps the package from crossing the same gate even when the happy-path command succeeds.

Authoring readiness

The authoring/* seam checks lane dependencies, claims, content leaves, source evidence, and the authoring review before assembly can become publishable.

Current-hash evaluation

eval/run.ts hashes the assembled tree, checks the entry Skill and workflow-kernel kind, verifies route and entry order, confirms the runtime manifest, and stores WorkflowRuntime certification evidence against that hash.

Readiness and publication

publish/lifecycle.ts combines unresolved candidates, authoring, evaluation, runtime, and publication evidence. Publication copies only an approved current-hash package; distribution remains a file-list preview.

Creator differential

differential/ compares candidate status, source/reference inventory, source hashes, normalized protocol, generated artifact inventory, and initial readiness between official and standalone observations in disposable projects.

Engine differential

differential/engine/ characterizes the pinned official Engine and compares Run state, actions, artifacts, trajectories, checkpoints, snapshots, evals, and classified errors. Semantic mismatches block certification.

SECTION 05

Interview practice: the short explanations

These are compact answers to common architecture questions. Expand them with the architecture diagrams in Sections 2 and 4 when the interviewer asks for detail.

What problem does it solve?

It turns loosely interpreted Skills into governed, authorable, resumable workflow packages and instances. The system keeps human-readable instructions while adding explicit authoring evidence, runtime state, contracts, and safe transitions.

Why not just use Markdown?

Markdown is excellent for method and progressive disclosure, but it does not by itself provide durable pending actions, stale-response rejection, route determinism, artifact provenance, or recovery after a process exits.

Why not build a full Agent?

The project does not need open-ended autonomy everywhere. It needs bounded, explainable domain workflows. Limiting the runtime’s authority makes certification, review, recovery, and distribution practical.

What is the most important design decision?

Two explicit authorities with different jobs: Authoring owns package content and lane evidence; WorkflowRuntime and Engine own generated-workflow routing, recovery, and committed Run state. Generated adapters remain projections.

What makes it durable?

Run state and pending actions are persisted, identity-bound, and recoverable outside the original process. Badger also certifies journals, locks, checkpoints, receipts, snapshots, repair policy, and transactional finalization; authoring evidence remains a separate package-construction concern.

What makes Primer Designer a good example?

It has independent Skills, conditional route choices, optional stages, expensive evidence-producing steps, human review boundaries, and repeated design/pool cycles—exactly where a contract and durable runtime add value.

Remember this ownership table

QuestionOwnerReason
What should the package and workflow mean?Authoring content plus Workflow ProtocolAuthoring supplies domain judgment; the executable protocol makes the accepted meaning declarative, reviewable, and versioned.
Which action is legal next?WorkflowRuntime resolver over Engine stateRouting needs one deterministic authority and persisted identity.
What counts as complete?Output Schema, required evidence, and guardrailsCompletion is a contract, not a claim in prose.
Who performs the work?Human, Agent, script, or external executorThe runtime governs admissibility; it need not own every domain operation.
Can the package or result be trusted or delivered?Authoring evidence, runtime evidence, eval, certification, readiness, approvalContent quality, execution success, and release readiness are separate claims.

“The project is not trying to eliminate probabilistic behavior. It is trying to put probabilistic behavior in the right place. An Agent can reason within a Node and use the allowed Skill or tools, but the workflow contract and runtime decide the boundaries: current action, required evidence, legal transition, durable identity, and recovery state.”
