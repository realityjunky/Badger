SECTION 01第 01 节

Badger in one page一页读懂 Badger

A Skill is a Markdown method that an Agent follows. It is easy to write and move, but nothing guarantees which step comes next, what counts as done, or how to continue after a crash. Badger adds those guarantees and leaves the reasoning inside each step to the Agent. It turns Skills into a workflow package with declared steps, then runs the package through a single runtime that checks and records every step.

Skill 是 Agent 照着执行的 Markdown 方法说明，写起来简单、搬起来方便，但没有任何机制保证下一步做什么、怎样才算完成、崩溃后如何接着做。Badger 补上这些保证，同时把每一步内部的推理仍交给 Agent：它把 Skill 组合成声明了步骤的工作流软件包，再由唯一的运行时逐步检查并记录。

1.1 How Badger works1.1 Badger 如何工作

Build time: Creator构建期：Creator

An Agent and the badger CLI turn a goal and explicitly named source Skills into a reviewed workflow package. The Agent supplies the meaning. The CLI validates, hashes, and writes only after you confirm (§3).

Agent 与 badger CLI 一起，把目标和明确指定的源 Skill 变成经过审查的工作流软件包。含义由 Agent 提供；CLI 负责校验和计算哈希，并且只在你确认后写入（§3）。

Run time: WorkflowRuntime运行期：WorkflowRuntime

One runtime executes the package as a durable Run. It proposes one action at a time, a person, Agent, or script performs it, and the runtime accepts the result only after checking it (§4).

唯一的运行时把软件包作为持久化 Run 执行：每次只提出一个动作，由人、Agent 或脚本完成，运行时检查结果无误后才接受（§4）。

Only one thing passes between the two halves: the assembled package, its immutable snapshot, and their hashes. Neither half reads or writes the other's internal state.

两半之间只交接一样东西：组装好的软件包、它的不可变快照及其哈希。任何一方都不读写对方的内部状态。

The repository also holds a collaborative service around this kernel: its server, which signs people in, audits every write, keeps a workflow version's records from Sources through publication, and mirrors the Runs of published packages and checks their events against those records (§5.4); its web dashboard (§5.5); the Badger MCP's expert, engineer, and operator profiles for Agents (§5.6); and a host installer that puts published packages and the Badger MCP into Agent hosts (§5.7).

仓库中还有围绕这一内核的协作服务：其 server 负责登录、审计每一次写入，保存工作流版本从“来源”到发布的各项记录，并同步已发布软件包的 Run、按这些记录核对其事件（§5.4）；其 Web 仪表盘（§5.5）；供 Agent 使用的 Badger MCP 领域专家、工程师与运行者 profile（§5.6）；以及把已发布的软件包和 Badger MCP 装入 Agent 宿主的宿主安装器（§5.7）。

Team workflows. §7 explains the collaborative service: durable questionnaires, dossier and plan drafting, approval gates, published packages, Runs through local Agents and WorkBuddy, and team notifications.

团队工作流。§7 介绍协作服务：持久问卷、档案与计划起草、审批门槛、已发布软件包、通过本地 Agent 和 WorkBuddy 执行的 Run，以及团队通知。

1.2 Three rules behind most of the design1.2 贯穿设计的三条规则

1 · Nothing is written without confirmation1 · 未经确认，不写任何东西

Commands that only inspect never write. The first write is init --confirm. After that, generating, recording lane results, assembling, approving, and publishing each need their own --confirm, and so does the distribution preview. In the service, the Workflow owner confirms package approval and publication separately.

只做检查的命令从不写入。第一次写入是 init --confirm；此后生成、记录 lane 结果、组装、批准和发布都各自需要 --confirm，分发预览也一样。在服务中，工作流负责人分别确认软件包批准与发布。

2 · Only WorkflowRuntime moves a Run2 · 只有 WorkflowRuntime 能推进 Run

People, Agents, and scripts do the work and submit results. The runtime alone decides whether to accept a result and what happens next. Generated scripts only forward to it.

人、Agent 和脚本负责干活并提交结果；是否接受、下一步做什么，只由运行时决定。生成的脚本只是把请求转交给它。

3 · Evidence belongs to one hash3 · 证据只对一个哈希有效

Evaluation, review, and approval count only for the exact package hash they examined. Change any file and that evidence goes stale until you rerun it.

评估、审查和批准只对它们检查过的那个软件包哈希有效。改动任何文件，这些证据就会过期，必须重新执行。

1.3 When Badger fits1.3 什么时候适合用 Badger

Use Badger when the steps and what counts as done can be written down in advance, even if the work inside a step still needs an Agent, a tool, or a person. A plain Skill is enough when you need no guarantees. A general Agent runtime fits better when the route itself has to be invented while running.

如果步骤以及“怎样算完成”能事先写清楚——哪怕每一步内部仍需要 Agent、工具或人来完成——就适合用 Badger。如果不需要任何保证，普通 Skill 就够了；如果路线本身要在运行中临时规划，通用 Agent 运行时更合适。

SECTION 02第 02 节

The workflow contract工作流契约

A Badger workflow is declared, not improvised. The Workflow Protocol is normalized from the plan and stored in the package as reference/workflow-protocol.json. It names every Node, what each Node must prove, and which moves are legal. WorkflowRuntime executes only what the Protocol declares.

Badger 工作流是事先声明的，而不是临场发挥的。Workflow Protocol 由计划规范化而来，存放在软件包的 reference/workflow-protocol.json 中，列出每个 Node、每个 Node 需要证明什么，以及哪些流转合法。WorkflowRuntime 只执行 Protocol 声明的内容。

2.1 Nodes and their relationships2.1 Node 及其关系

These are the relationships a plan expresses. The questionnaire and the authoring lanes use the same terms (see also GLOSSARY.md).

以下是计划所表达的关系，问卷和创作 lane 使用同一套术语（另见 GLOSSARY.md）。

Node
One stage of the workflow, with its own responsibility, completion evidence, and outcomes. Its kind says why it exists: producer (produces artifacts and evidence), action (performs work), decision (asks the workflow owner), handoff (passes evidence on), guardrail (enforces a check), or control (routing structure).工作流中的一个阶段，有自己的职责、完成证据和可能的结果。kind 说明它为何存在：producer（产出产物与证据）、action（执行工作）、decision（询问工作流负责人）、handoff（传递证据）、guardrail（执行检查）或 control（路由结构）。
Implementation bindingImplementation binding（实现绑定）

2.2 What stays fixed and what stays flexible2.2 哪些固定，哪些灵活

  • Fixed: the graph of Nodes and transitions, what each Node must prove, and which decisions exist. Routing accepts only declared fields and values, using exact matches and at most one fallback. Ambiguous routes, undeclared values, undeclared loops, and unreachable required Nodes are rejected before any Run starts.
  • Flexible: how the work inside a Node gets done. A person, Agent, script, or tool may do it, and an Agent's reasoning may differ from run to run. Badger checks only the result.
  • 固定：Node 与转换构成的图、每个 Node 需要证明的内容，以及有哪些决策。路由只接受声明过的字段和值，采用精确匹配，最多一个回退分支；有歧义的路由、未声明的值、未声明的环和不可达的必需 Node，在任何 Run 开始前就会被拒绝。
  • 灵活：Node 内部的工作怎么完成。可以由人、Agent、脚本或工具完成，Agent 的推理每次可以不同，Badger 只检查结果。

Anything beyond a simple linear workflow is an opt-in capability: branches, decisions, Cycles, versioned artifacts, and durability options such as locks, journals, and checkpoints (§6.1). Turn one on only when the domain needs that extra proof.

简单线性工作流之外的功能都是可选的 capability：分支、决策、Cycle、产物版本，以及锁、日志、检查点等持久化选项（§6.1）。只有领域确实需要这层额外保证时才启用。

2.4 Example: Primer Designer2.4 示例：Primer Designer

Primer Designer is the first domain workflow planned on Badger. This section shows only its contract, not biological execution or a published package. It composes three independent Skills, genome-download, primer-design, and primer-pool-add, into 26 Nodes in four phases.

Primer Designer 是计划在 Badger 上构建的第一个领域工作流（这里只展示契约，不涉及生物学执行或已发布的软件包）。它把三个独立 Skill——genome-download、primer-design、primer-pool-add——组合成分四个阶段的 26 个 Node。

Read it left to right. Preparation fixes the scenario and inputs before any side effect. The handoff reconciles warnings and provenance, then offers a declared choice. The division of labor is the point. 3.2 Phase 1: agree on meaning3.2 第 1 阶段：确认含义

Sources are closed-world. Badger never searches for Skills. You declare each one by name and location in skillSources, and the source check, badger source-check (badger candidates is kept as an alias), inspects exactly those Skills, read-only. It reports each source's identity hash, an inventory of every file in that identity, configuration included, with its hash, the source's references and scripts, the files it ignored, and any blockers. Identity covers every file except a fixed, documented list of operating-system metadata, editor state, and interpreter caches (for example .DS_Store, .idea/, and __pycache__/). Those files stay out of both the hash and the inventory, so adding or removing one changes neither a proposal nor a package, and the source check lists them under ignored. A script's side effects (none, local-writes, network, scheduler-submission, installs) are declared in the source manifest or the plan's skillSources, and an undeclared script is reported as undeclared. A relative location must stay inside the project. An absolute location must stay inside the project or a root the host registers with --source-root or BADGER_SOURCE_ROOTS; a plan or a manifest cannot register roots itself. A missing, ambiguous, or out-of-scope source becomes a blocker; Badger never guesses.

来源是封闭的。Badger 从不自行查找 Skill：每个 Skill 都要在 skillSources 里以名称和位置声明，来源检查 badger source-check（badger candidates 保留为别名）只读地检查这些 Skill，报告每个来源的身份哈希、由构成身份的每个文件（包括配置）及其哈希组成的文件清单、该来源的参考资料与脚本、被忽略的文件，以及所有阻塞项。身份覆盖除一份固定且有文档记录的操作系统元数据、编辑器状态和解释器缓存清单（例如 .DS_Store、.idea/ 和 __pycache__/）之外的每个文件。这些文件既不计入哈希，也不进入文件清单，因此增删它们既不改变提案，也不改变软件包；来源检查把它们列在 ignored 下。脚本的副作用（none、local-writes、network、scheduler-submission、installs）在来源清单或计划的 skillSources 中声明；未声明的脚本会报告为未声明。相对位置必须留在项目内。绝对位置必须留在项目内，或宿主用 --source-root 或 BADGER_SOURCE_ROOTS 注册的根目录内；计划和来源清单都不能自行注册根目录。缺失、有歧义或超出范围的来源会成为阻塞项，Badger 从不猜测。

SECTION 04第 04 节

Run a workflow with WorkflowRuntime用 WorkflowRuntime 运行工作流

A Run is one durable execution of a package. It lives in files, not in a process or a conversation, so any later process can pick it up. The runtime and the worker take turns: the runtime proposes exactly one action, the worker performs it, and the runtime accepts or rejects the result.

Run 是软件包的一次持久化执行。它存在于文件中，而不在某个进程或对话里，所以之后任何进程都能接着运行。运行时与工作者轮流行动：运行时只提出一个动作，工作者完成它，运行时再决定接受还是拒绝结果。

  1. Start. start validates the Protocol and Run location, compiles the active Nodes into Engine steps, snapshots the package, and persists revision 0 with the first pending action.

    启动。start 校验 Protocol 和 Run 位置，把活动 Node 编译成 Engine 步骤，为软件包制作快照，并持久化 revision 0 及第一个待处理动作。

  2. Perform. The host reads the continuation. A person, Agent, or script does the work outside the runtime and collects artifacts and evidence.

    执行。宿主读取 continuation；人、Agent 或脚本在运行时之外完成工作，收集产物和证据。

  3. Submit. submit hands in the result for the pending action. The runtime checks it (§4.2) before changing anything.

    提交。submit 为待处理动作交回结果；运行时先检查（§4.2），再做任何改变。

  4. Advance. An accepted result is recorded, the revision goes up by exactly one, and the resolver picks the next Node, Cycle, or Attempt.

    推进。被接受的结果会被记录，revision 恰好加一，resolver 选出下一个 Node、Cycle 或 Attempt。

4.2 What submit checks4.2 submit 检查什么

A result changes nothing until it passes all of these checks:

结果必须全部通过以下检查，才会改变任何东西：

  • Identity. It must answer the current pending actionId. Decision answers, and every submission to a Run with durability features, must also quote the current revision, Run id, and execution identity. A mismatch is rejected and changes nothing, so a replayed submission can never advance the Run twice.
  • Completion. The Node's Output Schema artifacts and evidence, required Skill calls, enforced augmentations, and guardrails must all be satisfied. Proof of completed checks goes in evidence.completedChecks.
  • Artifacts. Each required versioned output names either one declared file update or one exact accepted version. Badger never picks “the latest file.”
  • Route. Routing values must be declared, and exactly one transition may match.
  • 身份。必须回答当前待处理动作的 actionId。决策回答，以及对启用了持久化能力的 Run 的所有提交，还必须注明当前的 revision、Run id 和执行身份。不一致的提交会被拒绝且不改变任何东西，所以重放的提交永远不会让 Run 前进两次。
  • 完成。该 Node 的 Output Schema 产物与证据、必需的 Skill 调用、强制型增强和 Guardrail 都必须满足；已完成检查的证明放在 evidence.completedChecks 中。
  • 产物。每个必需的版本化输出，要么指明一次声明过的文件更新，要么指明一个确切的已接受版本。Badger 从不自动选“最新的文件”。
  • 路由。路由值必须是声明过的，并且只能匹配到一条转换。

A missing prerequisite returns blocked with the same pending action, so you resubmit corrected evidence without redoing the work. A failed outcome (status: "failed") follows the Engine's retry policy, and the repair policy too if it is enabled.

缺少前置条件时返回 blocked，待处理动作保持不变，补齐证据后重新提交即可，无需重做工作。失败的结果（status: "failed"）按 Engine 的重试策略处理；若启用了修复策略，也按修复策略处理。

4.3 Decisions4.3 决策

A decision Node becomes a persisted ask_user action. Its await-user continuation carries the stable question and choices, the input schema, the rationale policy, and the reviewer requirement. Only submit can answer it, and the answer must match the revision, action, Node, Cycle, Attempt, package identity, choice, reviewer, inputs, rationale, and any required artifact or evidence references. An accepted answer creates one Decision Receipt and follows only the chosen transition. A stale, replayed, or mismatched answer changes nothing. If an artifact that the question refers to changes after the question is asked, the answer is stale too.

决策 Node 会变成持久化的 ask_user 动作，其 await-user continuation 包含固定的问题与选项、输入 Schema、理由要求和审查者要求。只有 submit 能回答它，回答必须与 revision、动作、Node、Cycle、Attempt、软件包身份、选项、审查者、输入、理由，以及所需的产物或证据引用全部一致。被接受的回答生成一张 Decision Receipt（决策回执），并且只沿所选的转换前进。过期、重放或不匹配的回答不会改变任何东西；如果问题所引用的产物在提问后发生了变化，回答同样作废。

4.5 Recovery and durability4.5 恢复与持久化

Every committed change goes through protected, bounded, atomic writes, and a failed write never replaces the last valid state. A workflow's durability profile can opt into stronger guarantees:

每次提交的变更都经过受保护、有边界的原子写入，写入失败绝不会覆盖最后一个有效状态。工作流的持久化配置还可以选择更强的保证：

  • Transition journal: a write-ahead record of the previous and intended files. While it is pending, resume and submit return recovery-required. A committing writer replaces the journal at each step, so a reader that finds it changed mid-read reads it again, as often as one transition can replace it, instead of failing (#89).
  • Mutation lock: one mutating operation per Run at a time. A lock is never stolen, and only recover may clear one whose owner process is proven gone. A lock names its host by a hashed identity of the boot and the process namespace, not by the hostname, so renaming the host keeps it attributable. An owner on another boot, namespace, or host, or one whose identity cannot be read, stays unknown, and recover refuses it too (#32, ADR 0018).
  • Verified checkpoints: content-addressed manifests written after each commit. Recovery falls back to an older checkpoint only when the history proves that nothing later was committed.
  • Also available: content snapshots of declared project files, verification receipts, a repair policy (a finite failure budget, then ask or stop), and transactional finalization (preview, confirm, apply, reconcile).
  • Transition journal（转换日志）：预写式记录变更前后的文件内容。日志未处理完时，resume 和 submit 返回 recovery-required。正在提交的写入方每一步都会替换日志，因此读取方发现日志在读取途中变了时会重新读取，次数足以覆盖一次转换的全部替换，而不是直接失败（#89）。
  • Mutation lock（变更锁）：同一时刻每个 Run 只允许一个变更操作。锁从不被强占；只有 recover 能清除那些已证实持有进程不存在的锁。锁以开机实例与进程命名空间的哈希身份而非主机名标识所在主机，因此主机改名后归属依然可识别。持有者若属于另一次开机、另一个命名空间或另一台主机，或其身份无法读取，就保持未知，recover 同样拒绝接管（#32，ADR 0018）。
  • Verified checkpoints（验证检查点）：每次提交后写入内容寻址的清单；只有当历史证明之后没有任何提交时，恢复才会退回到较早的检查点。
  • 其他可选项：对声明的项目文件做内容快照、验证回执、修复策略（有限的失败预算，用完后询问或停止），以及事务式终结（预览、确认、执行、对账）。

recover works only from the persisted records, never from chat history or generated files. It rolls known interrupted writes forward, leaves unknown material untouched and blocked, and never repeats external work.

recover 只依据持久化记录工作，从不依赖聊天记录或生成的文件。它把已知的中断写入向前补完，不碰未知内容并保持阻塞，也从不重做外部工作。

Dossier versions (#50). A signed-in Engineer or Administrator writes only the topic summaries, the Node responsibilities, and, for an upgrade, the upgrade source's recovery; the workflow's identity, the pinned sources, the facts, the deferred resolutions, and their provenance come from the records. Composing is refused while readiness has blockers, and the preview shows the kernel's findings, which must be repaired before a version is stored. The kernel writes the dossier and the ledger it relies on as canonical JSON, whose SHA-256 is the version's hash; the service stores that text once and never edits it. The latest entry in an append-only list of heads names the current version: composing content identical to it returns it unchanged, new content adds a version, and content identical to an earlier version selects that version again. Each new head is audited and asks the Workflow owner for approval, and the Workflow owner or an Administrator approves its exact hash through the shared gate protocol; the dossier's own confirmed flag approves nothing. A new head, like a change to the records the dossier relies on, supersedes the approval in the writer's transaction, invalidates the later stages, and notifies the Engineer and the Workflow owner; superseded versions and their approvals stay readable. Personal access tokens may read dossiers but never compose or approve one. Each source in a dossier is identified by its Project-relative location and its content hash, never by a server storage path, so restoring the storage elsewhere keeps an approved proposal current; a dossier stored before this reads without its storage paths, and its approvals authorize no further authoring until it is composed and approved again, followed by its plan and proposal (#89). Migration 0016 stores the versions and their heads (ADR 0023).

档案版本（#50）。以人的身份登录的工程师或管理员只撰写主题摘要、Node 职责，以及升级时升级来源的恢复方式；工作流身份、已固定的来源、事实、延后问题的处理结论及其出处都取自记录。就绪状态有阻塞项时拒绝编制；预览列出内核的 finding，修复后才能保存版本。内核把档案及其所依赖的账目写成规范化 JSON，其 SHA-256 就是版本的哈希；服务只保存一次这段文本、从不修改。当前版本由一份只追加的指针列表中最新的一条指明：编制出的内容与当前版本相同时，原样返回当前版本；内容是新的，就新增一个版本；与某个较早的版本相同，就重新选中那个版本。每新增一条指针都会写入审计，并请工作流负责人批准，由工作流负责人或管理员通过共用的门槛协议批准这个确切的哈希；档案自身的 confirmed 标记不代表任何批准。新增指针与档案所依赖记录的变化一样，会在写入的同一事务中取代批准、使后续阶段失效，并通知工程师和工作流负责人；被取代的版本及其批准记录仍可阅读。个人访问令牌可以读取档案，但不能编制或批准。档案中的每个来源以其相对于项目的位置和内容哈希标识，从不包含服务端存储路径，因此把存储恢复到别处后，已批准的提案仍是当前的；此前保存的档案在读取时不显示其存储路径，它的批准也不再授权后续创作，直到重新编制并批准该档案，再重新保存并批准其计划和提案（#89）。迁移 0016 保存这些版本及其指针（ADR 0023）。

Drafting jobs (#55). A signed-in Engineer or Administrator requests a job of one kind, at first drafting questions or follow-ups for a draft round. The job binds a context bundle to hashes (the version's frame, the pinned Skill versions and their inventories, the source study, the questionnaire's records and submitted answers, and the kernel's ledger and readiness, never a private draft), stores its output schema, and moves from queued to claimed to submitted, then accepted or rejected. An Agent with an engineer token lists, claims, submits, and releases jobs: a claim quotes the job's revision and returns its context, schema, a 30-minute lease, and the exact files of the pinned Skills its kind reads, and a result, at most 1 MiB, is checked against the stored schema. A claim whose files exceed twice the upload limit is refused with 413, and the job stays queued. An expired lease returns the job to the queue, and the job is cancelled only when the inputs its kind reads change, such as the pins, the round, and the questions for question drafting. A submitted result is only a set of suggestions: the Engineer edits or removes them and accepts or rejects the batch with a hash-bound confirmation, and only that acceptance creates draft questions; accepting follow-ups neither publishes a round nor resolves the parent. Every job action is audited with its person, token, channel, and Agent host. Migration 0017 stores the jobs.

起草作业（#55）。以人的身份登录的工程师或管理员按类别请求作业，最初的类别是为某个草稿轮次起草问题或追问。作业把上下文包绑定到哈希（版本框架、已固定的 Skill 版本及其文件清单、源文件研读、问卷记录与已提交的回答，以及内核的账目与就绪状态，从不包括私有草稿），保存其输出 Schema，并依次经过排队、已领取、已提交，最后被接受或拒绝。持 engineer 令牌的 Agent 可以列出、领取、提交和释放作业：领取时须给出作业的修订号，并得到其上下文、Schema、30 分钟的租约，以及该类作业所读取的固定 Skill 的原样文件；提交的结果不超过 1 MiB，并按保存的 Schema 校验。领取的文件总量超过上传上限的两倍时，以 413 拒绝，作业仍留在队列中。租约过期后作业回到队列；只有该类作业所读取的输入变化时，作业才会被取消，例如起草问题时的固定集合、轮次和已有问题。提交的结果只是一组建议：工程师编辑或删除其中的条目，再以绑定哈希的确认接受或拒绝整批，只有这次接受才会创建草稿问题；接受追问既不发布轮次，也不处理父问题。每个作业操作都会连同其人员、令牌、渠道和 Agent 宿主写入审计。迁移 0017 保存这些作业。

Structured answers and attachments (#51). A question may ask for free text, a single or multiple choice, yes or no, a number in a fixed unit, a table with named columns, or a file. The type belongs to the question revision, so revising it requires a new answer, and older text-only answers stay free text; the server validates every answer against its type. Any answer may carry attachments: PDF, PNG, JPEG, UTF-8 text, CSV, or JSON, checked by their content, at most 5 MiB each and eight files or 20 MiB per answer, stored in the content-addressed blob store. A file stays private to its uploader until a submitted answer uses it, and downloads follow the current workflow roles. A resolution preview binds the structured values and the attachments' hashes, and each fact keeps the receipts of the answer revisions it restates, so a corrected value or file needs re-confirmation. Migration 0018 stores the values and receipts (ADR 0024). Each person may leave at most eight unreferenced uploads, 20 MiB in all, on one question, and one more is refused with 413, naming both limits. The worker removes an upload that no answer revision, not even a draft, has referenced within BADGER_ANSWER_ATTACHMENT_RETENTION_SECONDS, one day by default, records each removal in Activity, and removes its content unless another attachment or a Skill version uses it; an upload that any revision references, inherited ones included, is never removed. Migration 0032 permits that deletion and no other (#89).

结构化回答与附件（#51）。问题可以要求自由文本、单选或多选、是或否、带固定单位的数字、带指定列的表格，或一个文件。回答类型属于问题的修订，因此改动类型就需要重新作答，较早的纯文本回答仍按自由文本处理；服务端按类型校验每个回答。任何回答都可以带附件：PDF、PNG、JPEG、UTF-8 文本、CSV 或 JSON，按内容核验，单个文件不超过 5 MiB，每个回答最多 8 个文件、共 20 MiB，存放在内容寻址的 blob 存储中。文件在被某个已提交的回答使用之前只有上传者可见，下载权限依据当前的工作流角色。处理结论的预览绑定结构化的值和附件的哈希，每条事实都保留其所重述回答修订的回执，因此更正值或文件后需要重新确认。迁移 0018 保存这些值和回执（ADR 0024）。每个人在同一个问题上最多可以留下 8 个、共 20 MiB 未被引用的上传，再上传就以 413 拒绝，并写明这两项上限。在 BADGER_ANSWER_ATTACHMENT_RETENTION_SECONDS（默认一天）内没有被任何回答修订（包括草稿）引用的上传，由 worker 删除，每次删除都记入活动日志；其内容也一并删除，除非另有附件或 Skill 版本使用同一内容。被任何修订引用的上传（包括继承来的）从不删除。迁移 0032 只允许这一种删除（#89）。

Plan versions (#58). Once the Workflow owner has approved a dossier, the kernel derives a FactoryPlan skeleton from it and the pins: the workflow's name, goal, and intent, the English artifact locale, the dossier's ordered Node identities, and the exact pinned sources with their script declarations. A signed-in Engineer or Administrator completes it as JSON with the kernel's findings shown live, and saves a version by quoting the preview's hash and the version the edit began from; an edit that changes the dossier, the Node identities, or the pinned sources cannot be saved, and concurrent saves conflict. As with dossiers, the latest head names the current plan version: saving content identical to it returns it unchanged, and saving an earlier version's content selects that version again. The Engineer may instead request a draft-plan job, whose result stays a suggestion until a signed-in Engineer accepts or edits it through the same checks. A plan version's canonical JSON binds the dossier version's hash, and the Workflow owner or an Administrator approves the exact plan and dossier hashes. A new plan version, or an earlier one selected again, is audited, supersedes that approval, and asks the Workflow owner to approve it; a replaced dossier, a changed fact, or a pin change invalidates it in the writer's transaction and notifies the Engineer and the Workflow owner. Personal access tokens may only read plans. Migration 0019 stores the versions and their heads (ADR 0025).

计划版本（#58）。工作流负责人批准档案后，内核依据档案和固定集合推导出 FactoryPlan 骨架：工作流的名称、目标和意图，英文的产物语言，档案中按顺序排列的 Node 身份，以及固定来源及其脚本声明的原样内容。以人的身份登录的工程师或管理员以 JSON 形式补全骨架，编辑时实时显示内核的 finding；保存版本时须给出预览的哈希和编辑起点的版本。改动档案、Node 身份或固定来源的编辑无法保存，并发保存会产生冲突。与档案一样，当前计划版本由最新的一条指针指明：保存的内容与当前版本相同时，原样返回当前版本；与某个较早的版本相同，就重新选中那个版本。工程师也可以请求 draft-plan 作业，其结果在以人的身份登录的工程师接受或编辑之前只是建议，并经过同样的检查。计划版本的规范化 JSON 绑定档案版本的哈希，工作流负责人或管理员批准的是计划和档案的确切哈希。新的计划版本或重新选中的较早版本会写入审计、取代这次批准，并请工作流负责人批准；档案被替换、事实变化或固定变化时，批准会在写入的同一事务中失效，并通知工程师和工作流负责人。个人访问令牌只能读取计划。迁移 0019 保存这些版本及其指针（ADR 0025）。

Source-study, restatement, translation, and import jobs (#56). Four more kinds use the same claims, schemas, and leases, and each accepted result is audited. A source-study job drafts source-derived facts and interfaces for one pinned Skill; accepting them creates the records through Source study's own evidence checks, and marking the Skill studied stays a separate confirmation. A restate-answer job drafts formal facts for an answered question; acceptance goes through the resolutions of #48, so the facts link to the current submitted answer revisions, take the workflow version's locale, and still await the expert's acknowledgement. A translate-question job translates a question into a chosen locale, and an accepted translation attaches to the question revision it translates without replacing its text. An import-open-questions job turns a pinned Skill's numbered open questions into draft questions that keep their source citation and original number; a numbered source question enters a workflow version at most once, and importing it again is refused with 409. Claims carry only the Skill files a kind reads: the job's Skill for source study and imports, every pin for questions, follow-ups, and plans, and none for restatements and translations. Likewise, only a change to its own inputs cancels a job, such as a source-study job's Skill pin and that Skill's study records, or a translation's question revision, so accepting another Skill's study or answering another question leaves it alone. Migration 0020 stores the kinds and their records.

源文件研读、事实重述、问题翻译与导入作业（#56）。另外四类作业沿用同样的领取、Schema 和租约，每个被接受的结果都会写入审计。source-study 作业为一个已固定的 Skill 起草源文件事实和接口；接受时通过“源文件研读”自身的证据检查创建记录，把该 Skill 标记为已研读仍是单独的一次确认。restate-answer 作业为已回答的问题起草正式事实；接受时走 #48 的处理结论流程，因此事实链接到当前已提交的回答修订，使用工作流版本的语言，并且仍需专家认可。translate-question 作业把问题译成指定的语言，被接受的译文附在它所翻译的问题修订上，不替换原文。import-open-questions 作业把已固定 Skill 中带编号的待解问题转为草稿问题，并保留其源文件引用和原编号；每个带编号的源问题在一个工作流版本中最多导入一次，再次导入会以 409 拒绝。领取时只附带该类作业所读取的 Skill 文件：源文件研读和导入作业附带其所针对的 Skill，起草问题、追问和计划的作业附带每个固定，事实重述和问题翻译作业不附带任何文件。同样，只有作业自身的输入变化才会取消它，例如源文件研读作业所针对 Skill 的固定及该 Skill 的研读记录，或翻译作业所针对问题的修订；因此接受另一个 Skill 的研读或回答另一个问题，都不会取消它。迁移 0020 保存这些类别及其记录。

WeCom group robot notifications and reminders (#57). A Workflow owner connects the team's WeCom group chat by pasting its robot's webhook URL and choosing the chat's language, and a Group lead may set a default robot for the Group's workflows; the nearest Group default applies unless the workflow has its own. Saving a robot is refused until the deployment sets BADGER_NOTIFICATION_KEY and BADGER_PUBLIC_URL, and a saved robot gets a test post. The URL is encrypted with BADGER_NOTIFICATION_KEY, shown masked, and never logged. Every committed action that creates inbox items queues one post per chat, which @mentions each recipient by the WeCom userid or mobile number they set in personal settings (a userid may contain @), unless they turned that event off; people with neither are named in plain text, a pending invitee as "Invited person" and never by email address, and everyone still gets their in-app items. Each action takes a random identity, so restoring a backup cannot make a new action collide with an earlier one. A post carries only the workflow's name, what is waiting, the counts, and a link, never answers, Skill content, or Run artifacts. The worker sends at most one post every 3.1 seconds per robot across all workers, tries five times with backoff, and uses the deployment's HTTPS proxy; after a rate-limited answer it waits at least 60 seconds, and rate-limited attempts do not use up the five, while a worker that lacks a setting records a failed attempt. The Delivery log records each post with how it mentioned each person (userid, mobile, or plain name), never the userid or mobile number itself; the Workflow owner and Administrators read a workflow's log, and a Group default's posts, test posts included, are recorded with that Group, whose leads and Administrators read its log. A failed post never blocks a gate. An item's requester, the Workflow owner, or an Administrator may Remind the people it still waits on, at most once per item per hour, and the reminder is audited with names and counts, never mention identifiers; without a robot, Remind offers Copy reminder, and a Remind whose post would reach nobody records nothing and offers Copy reminder instead. Tests post only to a stub robot; a post to a real team chat has not been checked yet. Migration 0021 stores the channels, preferences, deliveries, and reminders (ADR 0026).

企业微信群机器人通知与提醒（#57）。工作流负责人粘贴团队企业微信群机器人的 webhook URL 并选择该群的语言，即可接入该群；组长可以为组内工作流设置默认机器人，工作流没有自己的机器人时，使用最近一级组的默认机器人。部署设置 BADGER_NOTIFICATION_KEY 和 BADGER_PUBLIC_URL 之前，保存机器人会被拒绝；保存成功后会排入一条测试消息。该 URL 用 BADGER_NOTIFICATION_KEY 加密存储、遮蔽显示，且从不写入日志。每个产生收件箱条目的已提交操作，在每个群只排入一条消息，按接收人在个人设置中填写的企业微信 userid 或手机号 @ 他们（userid 可以包含 @），除非本人关闭了这类事件的提醒；两者都没有填写的人以纯文本列出姓名，尚待接受邀请的人称为“Invited person”，从不显示其邮箱地址；所有人仍会收到应用内条目。每个操作都有一个随机身份，因此从备份恢复后，新操作也不会与先前的操作冲突。消息只包含工作流名称、等待处理的事项、数量和链接，从不包含回答、Skill 内容或 Run 产物。worker 让每个机器人在所有 worker 之间每 3.1 秒最多发送一条，失败时退避重试、共尝试五次，并使用部署的 HTTPS 代理；遇到限流答复时至少等待 60 秒，限流的尝试不计入这五次；缺少某项设置的 worker 会记下一次失败的尝试。投递日志记录每条消息以何种方式提及每个人（userid、手机号或纯文本姓名），但从不记录 userid 或手机号本身；工作流负责人和管理员查看工作流的日志，组默认机器人的消息（包括测试消息）记在该组名下，由该组的组长和管理员查看。发送失败从不阻塞门槛。事项的发起人、工作流负责人或管理员可以“提醒”仍被等待的人，每个事项每小时最多一次，审计中只记录姓名和数量，从不记录用于提及的标识；没有机器人时，“提醒”改为提供“复制提醒”；消息不会送达任何人时，“提醒”不记录任何内容，同样改为提供“复制提醒”。测试只向模拟机器人发送，尚未在真实的团队群中验证。迁移 0021 保存通知渠道、偏好、投递和提醒（ADR 0026）。

Proposal approval and initialization (#59). For the approved plan version, the dashboard shows the kernel's proposal with its blockers, warnings, source identities, and hash. The Workflow owner or an Administrator approves it through the shared gate protocol, binding the proposal, the plan version, the dossier version, and the pins. A signed-in Engineer or Administrator then starts an initialization job by quoting the approved proposal hash, and replaces an existing Creator state only by also quoting that state's hash; the request returns at once, and repeating it returns the same job. The worker rechecks the approval, the plan, the sources, and the quoted state under the version lock, runs the kernel's initialization in a private namespace, and commits the new state's exact bytes and hash with the job's outcome, the stage changes, and the audit entry in one transaction; a failed job leaves the previous state current, and failed and cancelled jobs are audited too. The stored canonical JSON is authoritative over the plan file the kernel reads, so a materialized file that does not match it is rewritten from the database. Success finishes Plan and proposal and opens Package. A changed plan or a superseded dossier invalidates the proposal's approval, cancels unfinished initialization jobs, and notifies the Engineer and the Workflow owner. When the kernel's proposal hash changes on its own while an approval is active, as after a kernel upgrade, the Workflow owner's approval of the current proposal supersedes the stale one. Personal access tokens may read the proposal and its jobs but never approve or initialize. Migration 0022 adds the initialization jobs and the stored Creator states (ADR 0027).

提案批准与初始化（#59）。对已批准的计划版本，仪表盘显示内核给出的提案，包括其阻塞项、警告、来源身份和哈希。工作流负责人或管理员通过共用的门槛协议批准它，绑定提案、计划版本、档案版本和固定集合。随后，以人的身份登录的工程师或管理员给出已批准的提案哈希，启动初始化作业；只有同时给出现有 Creator 状态的哈希，才能替换该状态。请求立即返回，重复同一请求得到同一个作业。worker 在版本锁下重新核对批准、计划、来源和所给出的状态，在私有命名空间中运行内核的初始化，再把新状态的原样字节和哈希，连同作业结果、阶段变化和审计记录，在同一事务中提交；作业失败时，先前的状态仍是当前状态；失败和被取消的作业同样写入审计。数据库中保存的规范化 JSON 优先于内核读取的计划文件，因此物化出的文件与之不符时，会按数据库中的内容重写。成功后“计划与提案”阶段完成，“软件包”阶段开启。计划变更或档案被取代时，提案的批准失效，未完成的初始化作业被取消，并通知工程师和工作流负责人。如果在批准仍有效时内核自行改变了提案哈希（例如内核升级之后），工作流负责人对当前提案的批准会取代过时的那次批准。个人访问令牌可以读取提案及其作业，但不能批准或初始化。迁移 0022 加入初始化作业和保存的 Creator 状态（ADR 0027）。

Skill and workflow version changes (#52). Pinning a different Skill version compares the hashes of the files that questions, facts, and source-study records cite. A changed, removed, or unpinned file reopens the questions that cite it, deferred ones included, supersedes their facts, and marks source-derived facts stale, while unrelated file changes keep their confirmations; each affected record opens the old and the current file side by side. A question or follow-up may keep citing an earlier Skill version while the cited file is byte-identical in the current pin, and a resolution preview checks a follow-up's evidence and assignees, so a failing follow-up is refused before sign-off. Starting a new workflow version copies the latest version's pins, source study, questionnaire, answers, facts, acknowledgements, resolutions, linked drafts, accepted translations, and import provenance in one locked transaction, audited as workflow_version.inherited. Each copy keeps its state, flags included, and links to the version, record, and revision it came from, and later edits stay independent. Pending questionnaire inbox items move to the new version, and the earlier version's items close. Approvals, dossiers, plans, jobs, and round baselines are not copied: the new version queues its own source check and needs fresh gates, and superseded approvals stay visible as superseded. Migration 0023 stores the provenance (ADR 0028).

Skill 与工作流的版本变化（#52）。固定另一个 Skill 版本时，系统比较问题、事实和源文件研读记录所引用文件的哈希。被引用的文件有改动、被移除或其 Skill 不再固定时，引用它的问题（包括已延后的问题）重新打开，其事实被取代，源文件事实标记为过时；无关文件的变化保留原有确认。每条受影响的记录都可以并排打开旧文件和当前文件。只要被引用的文件在当前固定的版本中逐字节相同，问题或追问就可以继续引用较早的 Skill 版本；处理结论的预览会检查追问的依据和回答人，因此不合格的追问在签字之前就会被拒绝。开始新的工作流版本时，系统在一个加锁的事务中复制最新版本的固定、源文件研读、问卷、回答、事实、认可、处理结论、关联草稿、已接受的译文和导入出处，并以 workflow_version.inherited 写入审计；每份副本保留原有状态（包括标记），并链接到它所来自的版本、记录和修订，此后的编辑互不影响。待处理的问卷收件箱条目会移到新版本，较早版本中的这些条目随之关闭。批准、档案、计划、作业和轮次基线不会复制：新版本排入自己的来源检查，需要重新通过各道门槛；被取代的批准仍以“已被取代”显示。迁移 0023 保存这些出处（ADR 0028）。

Skill versions from registered Git repositories (#70). A Field expert or Engineer who may upload to a Skill's group registers an HTTPS Git repository for that Skill, which fetches nothing, and then imports one full commit hash; branches, tags, and abbreviated hashes are refused. Only origins listed in BADGER_GIT_ALLOWED_ORIGINS can be registered, a URL with ? or # is refused, the repository must be readable without credentials over Git's smart HTTP, and redirects are refused. Git runs with isolated configuration and no hooks, credential helpers, or checkout, within bounded time, bytes, and file counts, and nothing fetched runs; Git LFS content is refused. A server process runs at most two fetches at once and refuses another with 503 and Retry-After, and an unreachable Git host, a timeout, or a missing git binary also answers 503 unavailable. The committed files then take the upload path: the kernel's source check gives the hash and inventory, the person declares every script's side effects, and creation quotes the preview's hash. The same tree yields the same Skill version as a direct upload, and the version records each repository and commit it came from. The import fetches the repository's branches and tags with their history, within the same limits, and refuses a commit that none of them reaches; the record names a branch or tag that reaches it, and records from before this check name none (#89). BADGER_GIT_PROXY sends Git fetches through an HTTP or HTTPS proxy, and hosts listed in BADGER_GIT_NO_PROXY bypass it; an invalid proxy URL stops the server at startup, and proxy credentials never appear in logs or responses (#89). Migration 0024 stores the registrations and import receipts, and migration 0033 the branch or tag (ADR 0029).

从已注册 Git 仓库导入的 Skill 版本（#70）。可以向某个 Skill 所在组上传的领域专家或工程师，为该 Skill 注册一个 HTTPS Git 仓库（注册时不拉取任何内容），然后导入一个完整的提交哈希；分支、标签和缩写哈希都会被拒绝。只有 BADGER_GIT_ALLOWED_ORIGINS 列出的源才能注册，含有 ? 或 # 的 URL 会被拒绝，仓库必须无需凭据即可通过 Git 智能 HTTP 读取，重定向会被拒绝。Git 在隔离的配置下运行，不执行钩子、不使用凭据助手、不检出文件，耗时、字节数和文件数都有上限，拉取的内容从不运行；Git LFS 内容会被拒绝。每个 server 进程同时最多运行两次拉取，再有请求就以 503 和 Retry-After 拒绝；Git 主机不可达、超时或缺少 git 可执行文件时，同样以 503 unavailable 答复。提交中的文件随后走上传的流程：内核的来源检查给出哈希和文件清单，由本人声明每个脚本的副作用，创建时须给出预览的哈希。同一棵文件树与直接上传得到同一个 Skill 版本，该版本记录它来自的每个仓库和提交。导入时会在同样的上限内拉取仓库的分支和标签及其历史，并拒绝任何分支或标签都到达不了的提交；记录会写明一个能到达该提交的分支或标签，此项检查之前的记录则不写（#89）。BADGER_GIT_PROXY 让 Git 拉取经由 HTTP 或 HTTPS 代理进行，BADGER_GIT_NO_PROXY 中列出的主机绕过代理；代理 URL 无效时 server 在启动时即报错，代理凭据从不出现在日志或响应中（#89）。迁移 0024 保存仓库注册和导入回执，迁移 0033 保存该分支或标签（ADR 0029）。

Agent audit provenance (#79). Every request made with a personal access token, reads included, requires X-Badger-Agent-Host, a nonblank label of 1–200 printable ASCII characters; reads need it because some record audit events, such as returning an expired lease to the queue. Activity records the person, token ID, Agent host, and mcp channel for comments, concerns, Skill uploads, Engineer drafts, and every other permitted token request, and displays the host beside the channel. A missing or invalid host refuses the request with 400. Sessions, local credentials, and workers always have an empty audit host.

Agent 审计来源（#79）。每次使用个人访问令牌发出的请求（包括读取）都必须提供 X-Badger-Agent-Host，其值是 1–200 个可打印 ASCII 字符组成且不能全为空白的标签；读取也需要它，因为有些读取会记录审计事件，例如把过期的租约退回队列。评论、关切、Skill 上传、工程师草稿以及其他允许的令牌请求，都会在活动日志中记录本人、令牌 ID、Agent 主机和 mcp 渠道，主机显示在渠道旁。缺少或无效的主机标签会以 400 拒绝该请求。会话、本地凭据和 worker 的审计主机始终为空。

Package scaffold generation (#60). Once initialization has succeeded, a signed-in Engineer or Administrator previews generation at its gate, which binds the proposal, the Plan version, and the Creator state hashes, and confirms it; the generate request then quotes that confirmation and returns its job at once, and repeating it returns the same job. The worker rechecks the approved inputs and the Creator state under the version lock, runs the kernel's confirmed generator in a private Creator namespace under the same Project root, and commits the package inventory, the Authoring plan, and the new Creator state's exact bytes with the job's outcome, the stage changes, and the audit entry in one transaction. The bundled source Skills and the MCP-mode instructions come from the kernel's generator (§2.3, §4.6). The package view lists every file with its kernel owner, size, and SHA-256, previews a listed file of up to 1 MiB after checking its hash, and shows the Authoring plan. A change that invalidates the proposal, or a new initialization, withdraws the generation confirmation, cancels unfinished generation jobs, and marks the package invalid; a regeneration starts a new Authoring session and supersedes later Authoring, evaluation, and review work. Both notify the Engineer and the Workflow owner, and the earlier package stays readable. Personal access tokens may read packages but never confirm or generate. Migration 0027 adds the job kind and the packages (ADR 0030).

软件包脚手架生成（#60）。初始化成功后，以人的身份登录的工程师或管理员在生成门槛预览并确认生成，门槛绑定提案、计划版本和 Creator 状态的哈希；随后的生成请求须给出这次确认，并立即返回其作业，重复同一请求得到同一个作业。worker 在版本锁下重新核对已批准的输入和 Creator 状态，在同一项目根目录下的私有 Creator 命名空间中运行内核经确认的生成器，再把软件包文件清单、创作计划和新 Creator 状态的原样字节，连同作业结果、阶段变化和审计记录，在同一事务中提交。内置的源 Skill 和 MCP 模式说明都来自内核的生成器（§2.3、§4.6）。软件包视图列出每个文件及其内核所有者、大小和 SHA-256，核对哈希后可预览不超过 1 MiB 的已列出文件，并显示创作计划。使提案失效的变更或新的初始化，会撤回生成确认、取消未完成的生成作业，并把软件包标为失效；重新生成会开启新的创作会话，取代其后的创作、评估和审查工作。两者都会通知工程师和工作流负责人，较早的软件包仍可阅读。个人访问令牌可以读取软件包，但不能确认或生成。迁移 0027 加入生成作业类别和软件包记录（ADR 0030）。

Authoring lanes and assembly (#61). A signed-in Engineer or Administrator offers the kernel's ready lanes as authoring-lane drafting jobs, and its review lane as review-vote jobs; a lane becomes a job only when the kernel's dispatch allows it, so lanes arrive in Wave order. An Agent claims and submits them with the tools of #55: a claim carries the kernel's bounded handoff, bound to its context hash, and a result holds the kernel's lane output inline, at most 256 KiB, never naming a file on the service host. The Engineer previews accepting or rejecting a result against the job's revision, result, and input hashes, and a rejection keeps its reason. Acceptance replays the generation's accepted outputs through the kernel in a disposable namespace, records the new output, and commits the exact Creator bytes with the accepted revision and person, the job decision, the stage changes, and the audit entry together; a failed transaction leaves the previous session as it was. A NEEDS_CONTEXT result becomes a draft question for the Workflow owner in an Authoring round, and a BLOCKED result becomes a repair job for its lane, each linked to it; neither counts as a current lane. A changed dependency or generation cancels the affected jobs, while other lanes in the same Wave carry on. Assembly is a confirmed action for a signed-in Engineer or Administrator, bound to the Creator state and session revision and refused while any lane is missing or stale; it keeps the assembled hash and inventory, finishes Package, and opens Evaluation. Agents cannot accept a result or assemble. Migration 0028 adds the job kinds, the accepted outputs, and the follow-up links (ADR 0031).

创作 lane 与组装（#61）。以人的身份登录的工程师或管理员把内核判定为就绪的 lane 作为 authoring-lane 起草作业提供，把审查 lane 作为 review-vote 作业提供；只有内核的分派允许时，lane 才会成为作业，因此各 lane 按 Wave 顺序到来。Agent 使用 #55 的工具领取和提交这些作业：领取时得到内核绑定上下文哈希的有界交接材料，提交的结果以内联方式携带内核的 lane 输出，不超过 256 KiB，且从不指向服务主机上的文件。工程师对照作业的修订号、结果和输入哈希预览接受或拒绝，拒绝时保留理由。接受时，系统在一次性的命名空间中经内核重放该次生成已接受的输出，记录新的输出，再把 Creator 状态的原样字节，连同被接受的修订号与接受人、作业决定、阶段变化和审计记录一并提交；事务失败时，先前的会话保持原样。报告 NEEDS_CONTEXT 的结果会在一个创作轮次中变成指派给工作流负责人的草稿问题，报告 BLOCKED 的结果会变成该 lane 的修复作业，两者都与该 lane 关联，且都不算作当前的 lane。依赖或生成变化会取消受影响的作业，同一 Wave 中的其他 lane 照常进行。组装是以人的身份登录的工程师或管理员经确认才能执行的操作，绑定 Creator 状态和会话修订号，有任何 lane 缺失或过时就会被拒绝；组装保留组装后的哈希和文件清单，完成“软件包”阶段并开启“评估”阶段。Agent 不能接受结果，也不能组装。迁移 0028 加入这些作业类别、已接受的输出和后续关联（ADR 0031）。

Evaluations (#62). A signed-in Engineer or Administrator confirms an evaluation of the current assembled package hash, and the request queues an evaluate job bound to the package and the committed Creator state. The worker evaluates a clone of that state with the kernel's public evaluator, without persisting Creator state, writes each attempt's report in a directory of its own, and reports progress while certification runs outside any database transaction. Certification runs only the package's generated adapters, never its domain scripts, as child processes whose environment holds only PATH and synthetic inputs, with a private temporary directory: each child gets at most 15 seconds and 4 MiB of output, each adapter at most 512 MiB of data, its process tree is stopped above 512 MiB of resident memory, and the whole certification shares a 180-second deadline. It needs Linux and util-linux's prlimit, which the image includes, and fails closed without them. Completion rechecks the lease and the package under the version lock and commits the report with its package hash, checks, Authoring cross-validation, certification phases with their negative cases, duration, and starter, together with the stage change, the audit entry, and an inbox item for the starter. Reports are append-only, and SQL refuses to change or delete one. A passing report for the current package hash finishes Evaluation, and publication readiness overlays it on a clone of the Creator state and asks the kernel. An upstream change cancels queued and running evaluations, and earlier reports stay readable. Personal access tokens read evaluation status through the engineer profile but never start an evaluation. Migration 0029 adds the job kind and the reports (ADR 0032).

评估（#62）。以人的身份登录的工程师或管理员确认对当前组装后软件包哈希的评估，请求随即排入一个绑定该软件包和已提交 Creator 状态的评估作业。worker 用内核的公开评估器评估该状态的副本，不持久化 Creator 状态；每次尝试的报告写入各自的目录；认证在任何数据库事务之外运行，期间持续报告进度。认证只运行软件包生成的适配器脚本，从不运行领域脚本；这些脚本作为子进程运行，环境中只有 PATH 和合成输入，并使用私有的临时目录：每个子进程最多 15 秒、输出最多 4 MiB，每个适配器的数据分配最多 512 MiB，其进程树的常驻内存超过 512 MiB 即被终止，整个认证共用 180 秒的时限。认证需要 Linux 和 util-linux 的 prlimit（镜像已包含），缺少时直接失败。完成时，worker 在版本锁下重新核对租约和软件包，再把报告（含软件包哈希、各项检查、创作交叉校验、带负面用例的认证阶段、耗时和发起人），连同阶段变化、审计记录和给发起人的收件箱条目一并提交。报告只追加，SQL 拒绝修改或删除报告。当前软件包哈希有一份通过的报告时，“评估”阶段完成；发布就绪状态把这份报告叠加到 Creator 状态的副本上，交由内核判断。上游变化会取消排队中和运行中的评估，较早的报告仍可阅读。个人访问令牌可以通过工程师 profile 读取评估状态，但不能发起评估。迁移 0029 加入评估作业类别和报告记录（ADR 0032）。

Package review and publication (#63). For the current package hash, the review view shows the kernel's Authoring, runtime, and publication readiness, the approval history, and every published version. A signed-in Workflow owner or Administrator approves the exact assembled package and its passing evaluation through the shared gate protocol, then separately confirms publication using the same capability. Accepting Authoring lane results does not disqualify them, and no independence override is needed. On publication: the kernel checks the approved hash, current Authoring readiness, and the passing evaluation, and publishes into a disposable directory, and the service stores the published files, their inventory, and the package hash in an append-only record. Approval asks the Workflow owner to publish, and publication finishes Review and publication. Package reviews and published packages are immutable. A regeneration invalidates the current approval but never withdraws a published package, so each workflow lists all its published versions. Every retrieval of a published package checks its stored bytes and inventory with the kernel's snapshot verification. People who can read the workflow may retrieve it, and so may a personal access token with the operator or engineer scope for an Engineer or Administrator, or with the operator scope for an Operator. Tokens never approve or publish. Migration 0030 adds the reviews and publications; 0037 converts Reviewer bindings and pending invitations into Workflow owner and merges duplicates while retaining question recipients and invitation inbox items. This grants former Reviewers the owner’s full capabilities. ADR 0038 supersedes ADR 0033’s governance and retains its immutable publication design.

软件包审查与发布（#63）。审查视图针对当前软件包哈希显示内核给出的创作、运行时和发布就绪状态、批准历史，以及每个已发布的版本。以人的身份登录的工作流负责人或管理员通过共用的门槛协议批准确切的组装后软件包及其通过的评估，再使用同一权限单独确认发布。接受过创作 lane 的结果不影响其批准资格，也不再需要独立性越权理由。发布时，内核核对已批准的哈希、当前的创作就绪状态和通过的评估，发布到一个一次性目录中，服务再把发布的文件、其文件清单和软件包哈希保存在一条只追加的记录中。批准后会请工作流负责人发布，发布则完成“审查与发布”阶段。软件包审查记录和已发布的软件包都不可变。重新生成会使当前的批准失效，但从不撤回已发布的软件包，因此每个工作流都会列出它所有已发布的版本。每次读取已发布的软件包，都会用内核的快照校验核对其保存的字节和文件清单。能读取该工作流的人可以读取它；个人访问令牌带 operator 或 engineer 范围时可以为工程师或管理员读取，带 operator 范围时可以为运行操作员读取。令牌从不批准或发布。迁移 0030 加入审查和发布记录；0037 把原审查者绑定及待接受邀请转为工作流负责人，合并重复项并保留问题接收者与邀请收件箱条目。原审查者由此获得负责人的全部权限。ADR 0038 取代 ADR 0033 的治理规则，并保留其不可变发布设计。

Runs mirrored from the Badger MCP (#65). The local Badger MCP registers a Run only after WorkflowRuntime has accepted its start, and registration fixes the person, the host label, the Agent host, the publication, and the package hash; a replay must match them. The MCP then sends the Run's events in order with their sequence numbers, at most 64 per request, followed by the kernel's projection and continuation. The service stores each event once and never changes it, and refuses a gap, a changed duplicate, an identity change, a malformed read model, and anything over its limits: 2 MiB per request, 256 KiB per event, and 1 MiB per snapshot. It never evaluates routes, Completion, Cycles, or Attempts: it observes, and the Run root stays authoritative. Registering and reporting a Run needs an Operator role, or an Administrator, and with a token the operator scope; a test Run needs an Engineer role and the engineer scope instead. People who can read a workflow can read its Runs: each workflow's and each person's newest 100, and a Run's detail with its original events 500 at a time and its latest 256 recorded outcomes with their counts. Personal access tokens read Runs with the same access as published packages. Migration 0031 adds the Runs and their events (ADR 0035).

从 Badger MCP 同步的 Run（#65）。本地 Badger MCP 只在 WorkflowRuntime 接受启动之后才向服务登记 Run；登记固定人员、主机标签、Agent 宿主、发布和软件包哈希，重放的登记必须与之一致。MCP 随后按顺序发送 Run 的事件及其序号，每个请求最多 64 个，再发送内核的投影和 continuation。服务把每个事件只保存一次、从不修改，并拒绝缺口、内容变化的重复事件、身份变化、格式不正确的读模型，以及超过上限的内容：每个请求 2 MiB、每个事件 256 KiB、每份快照 1 MiB。它从不判断路由、Completion、Cycle 或 Attempt：它只是观察方，Run 根目录始终是权威记录。登记和上报 Run 需要运行操作员角色或管理员身份，使用令牌时还需要 operator 范围；测试 Run 则需要工程师角色和 engineer 范围。能读取工作流的人可以读取它的 Run：每个工作流和每个人最新的 100 个 Run，以及 Run 详情——原始事件每次 500 个，最近 256 条已记录的结果及其计数。个人访问令牌读取 Run 所需的权限与读取已发布软件包相同。迁移 0031 加入 Run 及其事件（ADR 0035）。

Run gates (#66). When a mirrored continuation waits on a person, for a decision, a repair manual stop, or a finalization confirmation, the service opens a durable gate for the Run, and a changed pending action supersedes the open gate and closes its inbox items. The published package's reviewer policy names who may answer, by stable Badger person IDs and the workflow authorities Workflow owner, Engineer, Field expert, and Operator (owners also satisfy the legacy reviewer authority in immutable published policies): every authority it requires must be held, a named person must hold it too, a policy that names none leaves the gate to Operators, and being an Administrator grants none of them. Inbox items and team robot posts link straight to the Run. A signed-in person who holds that authority previews an answer, a choice with any inputs and a rationale, bound to the Run's revision, Node, Cycle, Attempt, and pending action, and confirms it; the service attaches the person's attestation, records the answer immutably with its audit entry, and closes the gate's inbox items in one transaction, and repeating a request returns the original answer. Personal access tokens can neither preview nor answer a gate; only the registered person's MCP, on the registered Agent host, reads the answer to deliver it (§5.6). A finalization gate shows the kernel's exact planned operations, checked against the pending confirmation's hash, and changed effects need a fresh gate and a fresh answer. Migration 0034 adds the gates and answers (ADR 0036).

Run 门槛（#66）。同步来的 continuation 需要人来处理时——决策、修复中的手动停止或最终化确认——服务为该 Run 开启一道持久的门槛；待处理动作一旦变化，开启中的门槛即被取代，其收件箱条目随之关闭。已发布软件包的审查者策略指定谁可以作答，以稳定的 Badger 人员 ID 和工作流权限（工作流负责人、工程师、领域专家和运行操作员）表示；负责人也满足不可变的已发布策略中的旧 reviewer 权限：策略要求的每项权限都必须具备，被点名的人也必须具备该权限，未指定任何权限的门槛留给运行操作员，管理员身份本身不带有其中任何一项权限。收件箱条目和团队机器人的消息都直接链接到该 Run。具备该权限、以人的身份登录的人预览一个回答（一个选项，可附输入和理由），它绑定 Run 的修订号、Node、Cycle、Attempt 和待处理动作，然后确认；服务附上此人的身份证明，把回答连同审计记录不可变地保存，并在同一事务中关闭该门槛的收件箱条目；重复同一请求返回原先的回答。个人访问令牌既不能预览也不能回答门槛；只有已登记者的 MCP、在已登记的 Agent 宿主上，才能读取回答并交付（§5.6）。最终化门槛显示内核给出的确切计划操作，并按待确认项的哈希核对；影响一旦变化，就需要新的门槛和新的回答。迁移 0034 加入门槛和回答记录（ADR 0036）。

Run integrity and recovery (#67). The service flags a decision with no matching gate answer, a gap in the event sequence, and an execution that differs from the published package as findings on the Run, and audits each finding when it appears, changes, or is resolved. A decision counts as answered only when an immutable dashboard answer to the same pending action matches it, with its revision, Node, Cycle, Attempt, choice, inputs, scope, rationale, and the reviewer's attestation; repair and finalization decisions are compared in their kernel forms. An unanswered decision is still stored, so the Run's later events can arrive, and neither a later snapshot nor a recovery clears its finding. Registration refuses an execution identity that differs from the one the kernel compiles from the published protocol. A report with a gap or a changed execution identity is refused with 409: the service discards that request's events and snapshot and keeps only the finding and its audit entry. The MCP also reports the hash of the installed package bytes, and changed or unreadable bytes are flagged even when the Run first registers. A Run keeps one current finding of each kind, and earlier ones stay in the Activity log. A complete report that covers a gap resolves it, and one with the bound execution identity resolves a mismatch. A Run needs recovery while it has a finding or while its local WorkflowRuntime has reported an interruption, which only the registered person and Agent host may report. Each local recovery sends a request ID bound to the interruption it answers, and the service records its outcome once: settled when no finding and no runtime recovery finding remains, blocked otherwise. Run list and detail responses carry the findings, whether the Run needs recovery, and the latest outcome, and Auditors can read them and their Activity without write access. Migration 0035 adds the findings, the recovery state, and the immutable recovery records (ADR 0037).

Run 完整性与恢复（#67）。若出现没有对应门槛回答的决策、事件序列有缺口，或执行与已发布软件包不同，服务都会把它作为 finding 标记在 Run 上，并在 finding 出现、变化或解决时记入审计。只有当同一待处理动作在仪表盘中有一份不可变的回答、且其修订号、Node、Cycle、Attempt、选项、输入、范围、理由和审查者的身份证明都与决策一致时，该决策才算已回答；修复决策和最终化决策按内核的形式核对。没有回答的决策仍会保存，以便 Run 之后的事件能够到达；之后的快照或恢复都不会清除它的 finding。登记时，若执行身份与内核根据已发布协议编译出的身份不同，服务即拒绝登记。有缺口或执行身份变化的报告会以 409 被拒绝：服务丢弃该请求的事件和快照，只保留 finding 及其审计记录。MCP 还会上报已安装软件包字节的哈希；字节有变或无法读取时，即使是 Run 首次登记也会被标记。每个 Run 的每类 finding 只保留当前一条，之前的记录留在活动日志中。覆盖了缺口的完整报告会解决缺口，执行身份与绑定一致的完整报告会解决不一致。只要 Run 还有 finding，或其本地 WorkflowRuntime 报告过中断，该 Run 就需要恢复；只有已登记的人员和 Agent 宿主可以报告中断。每次本地恢复都会发送一个绑定到所处理中断的请求 ID，服务只记录一次其结果：既没有 finding 也没有运行时恢复 finding 时为“已完成”，否则为“受阻”。Run 列表和详情的响应包含这些 finding、该 Run 是否需要恢复，以及最近一次恢复结果；审计员无需写权限即可读取它们及相关活动。迁移 0035 加入 finding、恢复状态和不可变的恢复记录（ADR 0037）。

Read-only demo (#71). /demo/ beneath the base path serves the dashboard on synthetic fixtures for My work, Workflows, Questionnaire, Skills, Runs, Evaluations, and Activity, with its own /api/v1/ namespace. The server handles it after the Host and Origin checks and before sessions, tokens, the database, the worker, and stored files, so it needs no sign-in and reads no real record. It answers only GET and HEAD, refuses every other method with 405, and answers 404 for a record without a fixture instead of falling back to a live one. The fixtures in src/demo/fixtures.ts must stay synthetic.

Run recovery (#67). recover recovers a Run through the local WorkflowRuntime on the Run's own computer, and WorkflowRuntime stays the only recovery authority. Before it calls the runtime, the MCP adds a request ID, bound to the interruption notice it answers, to .badger/mcp-recovery.json in the Run root, a queue kept apart from the reporting queue. When the runtime reports after a call that the Run needs recovery, the MCP records a notice there with an ID that stays the same while the interruption does, and reports it even when an unfinished transition keeps the kernel from exporting a committed report; outcomes of a recovery that stays blocked go with it. Otherwise the queued requests go with the next complete report. When the interruption clears without a request that answers its notice, for instance after the scripts' recover, the next complete report names the notice as settled, which clears it without inventing a recovery outcome. Install locally offers POSIX commands for macOS/Linux and PowerShell commands for Windows, for both installation and removal. The host installer is the @realityjunky/badger-hosts package in packages/hosts/ (#64), and the paths below are relative to it. It installs a published package and the Badger MCP configuration into Claude Code, Codex, or WorkBuddy, at project or user scope, on the person's own computer. The service and the browser never write there, so the dashboard's Install locally gives a local command bound to the publication ID and package hash, and the operator profile's installation tools use the same adapter (§5.6). A preview downloads the publication, refuses redirects, verifies the bytes with the kernel's snapshot check, and lists every file and directory it would write or delete, with the expected current hash and the new hash and size, the MCP entry, and one digest; it never shows unrelated configuration. A commit needs explicit confirmation and that exact digest, takes a local lock, computes the preview again, and refuses stale content, a changed root, or an unsafe path before writing anything; each file goes through the kernel's contained atomic writer, and the installed directory is verified against the published hash. A commit is not a transaction across files, so an interrupted installation stays visible as a conflict to review and repair. 6.5 Artifact receipts and external roots6.5 产物回执与外部根目录

Declarations and their limits

An Output Schema declares externalRoots as a map of names to {"description": "..."}, with at most 32 roots per schema and per workflow. A name has at most 128 characters; a nonempty description has at most 1,000 characters. Every root is used by an artifact in its schema, and a shared name has the same description everywhere. A declaration holds no directory or path. Describe what the directory holds, where it usually lives, and who owns it: the description becomes the Agent's question.

Artifacts opt in with verification: "receipt". Only then may they use root and requireCurrentAttempt, including an explicit false. An omitted root means the Run root. Paths are relative to the selected root, permit only * wildcards, and reject absolute paths, empty or dot segments, traversal, NUL, and ?. Receipt verification streams SHA-256 and can verify large artifacts; other artifacts stay inside the Run root under the 2 MiB content cap.

Binding and discovery

The kernel's startRequirements(protocol) is read-only and needs no Run. The script adapter's status before start forwards it as startRequirements. After the person chooses and confirms all directories, the kernel's externalRoots start option binds the map once for the Run. In the script adapter, use init --external-root <name>=<directory>, once per root. See the §4.6 procedure. The binding is fixed for that Run; no directory is guessed or reused from another Run without asking.

The continuation and next expose the current Node's receiptOutputs: artifactId, paths, root: {name, path}, and requireCurrentAttempt. A null root name identifies the Run root. Recovery in a fresh process returns the same bound directories.

Receipts, freshness, and findings

Accepted Completion evidence stores evidence.artifactReceipts. Each receipt has artifactId; root: {name, path} for an external root (omitted for the Run root); absolute path; byte size; sha256; modification time mtimeMs; and producer, which contains runId, nodeId, cycleId, attemptId, actionId, and revision. Directory receipts hash a manifest of file hashes and directory entries, and their size sums the files.

There are at most 256 receipts per Completion and 256 entries per directory receipt, including the directory being verified. Each file is checked for freshness; an empty directory uses its own modification time. With requireCurrentAttempt: true, modification time must be at or after the Attempt's first persisted action. Retrying keeps that boundary; re-entering the Node starts a new Attempt. Copies that preserve old timestamps (cp -p, rsync -a) or a filesystem clock behind the host can make newly copied output appear stale: write outputs afresh during the Attempt.

  • artifact-stale-attempt: Workflow artifact <schema>.<artifact> is stale for this Attempt: <relativePath>. A carried version from another Attempt is stale too.
  • artifact-content-drift: Workflow artifact content drift detected: <versionId>. A stored version's current content no longer matches its receipt.
  • external-root-binding-required: a start binding is missing or invalid. The finding has requiredAction: "execute", operation workflow.start, and requiresUserDecision: true. Ask the person, confirm their directories, and start again.

Receipt verification refuses changes during a read (Workflow artifact <schema>.<artifact> changed during receipt verification), unsafe traversal, symbolic links, junctions, and special filesystem objects. Limits refuse with Output Schema artifacts exceed 256 receipts per Completion or Workflow artifact <schema>.<artifact> exceeds 256 receipt entries. A capture failure is wrapped as Workflow artifact <schema>.<artifact> receipt verification failed: <reason>.

What verification never does

Verification never copies, writes, or publishes a file; it grants no access beyond the declared paths and never attests which process wrote a file. A receipt records content identity and freshness evidence, not process provenance.

声明及其限制

Output Schema 通过 externalRoots 声明名称到 {"description": "..."} 的映射。每个 schema 和整个工作流最多各 32 个根目录；名称最多 128 个字符，非空说明最多 1,000 个字符。每个根目录必须被所属 schema 的产物使用，共享名称在各处的说明必须相同。声明不包含目录或路径。说明应交代目录存放什么、通常位于何处、归谁所有，因为它会成为 Agent 向运行者提出的问题。

产物通过 verification: "receipt" 启用回执验证，只有此时才能设置 root 与 requireCurrentAttempt，即便后者显式为 false 也一样。未指定根目录时使用 Run 根目录。路径相对于所选根目录，只允许 * 通配符，拒绝绝对路径、空或点路径段、越界、NUL 和 ?。回执验证以流式 SHA-256 校验大型产物；其他产物仍限于 Run 根目录并受 2 MiB 内容上限约束。

每次 Completion 最多 256 张回执，每张目录回执最多 256 个条目，包括被验证的目录本身。逐个检查文件的新鲜度；空目录检查自身修改时间。设置 requireCurrentAttempt: true 后，修改时间必须不早于该 Attempt 第一个已持久化动作。重试保持这一边界；重新进入 Node 会创建新 Attempt。保留旧时间戳的复制（cp -p、rsync -a）或慢于宿主的文件系统时钟，会使新复制的输出看似陈旧，应在 Attempt 内重新写入输出。

  • artifact-stale-attempt：Workflow artifact <schema>.<artifact> is stale for this Attempt: <relativePath>。沿用其他 Attempt 的版本同样被视为陈旧。
  • artifact-content-drift：Workflow artifact content drift detected: <versionId>。已记录版本的当前内容与回执不符。
  • external-root-binding-required：启动绑定缺失或无效。finding 包含 requiredAction: "execute"、操作 workflow.start 和 requiresUserDecision: true。应询问运行者、确认目录，再重新启动。

验证过程中内容变化（Workflow artifact <schema>.<artifact> changed during receipt verification）、越界、符号链接、junction 与特殊文件系统对象都会被拒绝。超限消息为 Output Schema artifacts exceed 256 receipts per Completion 或 Workflow artifact <schema>.<artifact> exceeds 256 receipt entries。捕获失败以 Workflow artifact <schema>.<artifact> receipt verification failed: <reason> 包装。

验证绝不执行的操作

验证从不复制、写入或发布文件，不授予声明路径之外的访问权，也不证明由哪个进程写入了文件。回执记录内容身份与新鲜度证据，不证明写入进程的来源。

7.4 The questionnaire as records7.4 以记录形式保存的问卷

Each workflow version has a questionnaire, filterable by Skill, topic, assignee, and status. A question deferred as internal to one Skill moves to that Skill's backlog. Deferred questions appear with their resolutions and do not block the dossier.

The five-part ledger is computed from these records: confirmed user facts, source-derived facts, Agent inferences, unresolved assumptions, and remaining questions. Round baselines show what changed. Readiness names blockers for scope and each dossier topic, including interfaces: unresolved questions, unconfirmed inferences or assumptions, pending acknowledgements, and disputes. Composing a dossier snapshots the ledger's record IDs and revisions as canonical version 2 JSON with its hash, validates it through the kernel, and requires readiness without blockers.

五类账目由这些记录自动计算：已确认的用户事实、源文件推导的事实、Agent 推断、未解决的假设和剩余问题。轮次基线显示变化。就绪检查按范围和各档案主题（包括接口）列出阻塞项：未解决问题、未经确认的推断或假设、待认可的事实和争议。编制档案时，把账目的记录标识和修订快照为第 2 版规范化 JSON 及其哈希，交由内核校验，并要求就绪检查没有阻塞项。

新工作流版本继承事实、处理结论和待处理问卷工作，并保留指向原记录的出处。固定更新的 Skill 版本时，会标记所引证据变化的记录，要求重新核验。原有批准保留在历史中，新版本需要重新批准。

On the next call, the MCP delivers the answer with the service's attestation of the person's identity and authority, bound to the pending action and Run revision.

  1. 在工具旁启动。

    运行操作员通过服务器上的 CLI Agent，或 macOS、Windows 笔记本上的 WorkBuddy，启动已发布的工作流。MCP 获取并校验确切的软件包，经内嵌的 WorkflowRuntime 启动，随后登记已接受的 Run 及其人员、主机、Agent 宿主和软件包哈希。

  2. 遵循运行时。

    下一动作给出 Node、本地 Skill 文本、所需的 Completion 证据与输出，以及待处理动作。提交经过与脚本适配器相同的检查：跳过 Node、缺少证据、非法路由、耗尽 Cycle 和过时产物都会被拒绝。

  3. 让团队掌握进度。

    已提交事件、状态、发现和产物回执自动同步到服务。持久的本地队列在网络中断后重试上报，不阻塞执行。Run 根目录始终是权威记录，仪表盘显示状态、Attempt、事件、回执和恢复需求。

  4. 由人回答门槛。

    决策、手动停止或最终化会为 Node 策略指定的运行操作员或工作流负责人打开门槛。本人在仪表盘中回答，MCP 在下一次调用时交付回答，并携带服务对其身份和权限的证明，绑定待处理动作和 Run 修订。

The Agent never supplies a reviewer identity or signs off. The service flags unattested decisions, gaps in event sequences, and package hashes that differ from the publication. Recovery runs locally through WorkflowRuntime, with its status visible to the team.

Agent 从不提供审查者身份或代人签字。服务会标记缺少人员证明的决策、事件序列缺口和与发布不一致的软件包哈希。恢复通过本地 WorkflowRuntime 执行，团队可以看到其状态。

7.6 Notifications7.6 通知

Everyone has an in-app inbox with unread, read, and done states and a deep link on each item. Items become done automatically when their question, acknowledgement, approval, or Run gate is handled. Assignments, answers, concerns, submitted drafts, evaluation results, and stage invalidations also create notifications. The same action produces the same notifications whether it came from the dashboard, the Badger MCP, or a Run.

每个人都有应用内收件箱，条目分为未读、已读和已完成，并带有直达链接。问题、认可、批准或 Run 门槛处理完成后，条目自动完成。指派、回答、关切、已提交草稿、评估结果和阶段失效也会产生通知。无论操作来自仪表盘、Badger MCP 还是 Run，相同动作都会产生相同通知。

  • Connect a team chat. The Workflow owner saves a WeCom Group robot webhook and chooses Chinese or English; saving sends a test post. A Group lead can set a default robot, which a workflow's own robot overrides. Webhook secrets are encrypted, masked, and never logged.
  • Send one post per action per chat. Posts name the workflow, what is waiting, recipient counts, and a deep link. They @mention recipients by WeCom userid or supported mobile number, honoring each person's event preferences. Answer text, Skill content, and Run artifacts stay in Badger.
  • Track delivery. The worker paces posts to the robot's rate limit and retries failures with backoff. Workflow owners and Administrators see recipients, attempts, status, and errors in the delivery log. A failed post leaves the in-app item available and never blocks a gate.
  • Remind someone. The requester, Workflow owner, or Administrator can remind the people still needed, at most once per item per hour, with an audit record. Without a robot, Copy reminder provides names and a ready-to-paste deep link.
  • 连接团队群聊。工作流负责人保存企业微信群机器人的 webhook，并选择中文或英文；保存会发送测试消息。组长可设置默认机器人，工作流自己的机器人优先。Webhook 密钥加密保存、遮罩显示，从不写入日志。
  • 每次操作向每个群发一条消息。消息包含工作流名称、待处理事项、收件人数和直达链接，按个人的事件偏好，通过企业微信 userid 或支持的手机号 @ 提及收件人。回答文本、Skill 内容和 Run 产物保留在 Badger 内。
  • 追踪投递。worker 按机器人限额控制发送速度，并以退避方式重试失败。工作流负责人和管理员可在投递日志中查看收件人、尝试次数、状态和错误。消息失败时应用内条目仍然可用，从不阻塞门槛。
  • 提醒相关人员。请求人、工作流负责人或管理员可提醒仍需参与的人，每个条目每小时最多一次，并保留审计记录。没有机器人时，“复制提醒”提供姓名和可直接粘贴的直达链接。

7.9 Deployment and data protection7.9 部署与数据保护

Deploy the Badger image as server and worker alongside Postgres 17, with separate persistent volumes for the database, stored files, and kernel workspaces. The server exposes the dashboard, versioned JSON API, and event stream through a reverse proxy under a configurable base path. The worker serializes each workflow version's kernel transitions and handles evaluations and notifications. Local single-user mode uses loopback access and PGlite on disk.

把 Badger 镜像作为 server 和 worker 两种角色，与 Postgres 17 一起部署，为数据库、存储文件和内核工作区分别配置持久卷。server 在可配置的基础路径下，经反向代理提供仪表盘、带版本的 JSON API 和事件流。worker 串行处理每个工作流版本的内核转换，并运行评估和通知。本地单用户模式使用回环访问和磁盘上的 PGlite。

The same deployment supports an existing AI platform's sign-in and launcher, or an organization's own identity provider. Configure identity, database and storage paths, base URL, allowed origins, bootstrap Administrators, outbound HTTPS proxy, and the channel-secret encryption key through the environment. Deployment-specific launcher entries and proxy routes live with the deployment. The health endpoint reports the revision, clean-build status, database reachability, and migration state. Operations include nightly database dumps, stored-file snapshots, and a rehearsed restore.

同一套部署支持现有 AI 平台的登录和启动入口，也支持组织自己的身份提供方。通过环境配置身份、数据库和存储路径、基础 URL、允许的来源、初始管理员、出站 HTTPS 代理和渠道密钥加密键。各部署的启动入口和代理路由由部署自身维护。健康端点报告修订、构建树是否干净、数据库可达性和迁移状态。运维包括每晚数据库备份、存储文件快照和恢复演练。

Cookie-authenticated writes require the same origin; Badger's cookies are Secure, HttpOnly, and SameSite=Strict. Personal access tokens are shown once, stored hashed, rate-limited, and audited. Uploads have size and count limits, reject unsafe paths and escaping links, and are never executed. Upload only workflow knowledge, not real Run data; artifacts stay on their execution host and are referenced by receipts. Secrets come from environment files or secret mounts and stay out of logs and packages.

使用 Cookie 认证的写入要求同源；Badger 的 Cookie 使用 Secure、HttpOnly 和 SameSite=Strict。个人访问令牌仅显示一次，以哈希保存，并限速、审计。上传有大小和数量限制，拒绝不安全路径和逃逸链接，且从不执行。只上传工作流知识，不上传实际 Run 数据；产物保留在执行主机，以回执引用。密钥来自环境文件或密钥挂载，不进入日志和软件包。

Every mutable record carries a revision, and a stale write returns the current revision as a conflict. The append-only Activity log records the actor, session or token, web/MCP/worker channel, target, before-and-after revisions or hashes, reason, and request ID. Administrators and Auditors can inspect the full history.

每个可变记录都有修订号，过时写入会返回包含当前修订的冲突。只追加的活动日志记录操作人、会话或令牌、Web/MCP/worker 渠道、对象、前后修订或哈希、理由和请求标识。管理员和审计员可查看完整历史。
