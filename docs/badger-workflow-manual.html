SECTION 01第 01 节

Badger in one page一页读懂 Badger

A Skill is a Markdown method that an Agent follows. It is easy to write and move, but nothing guarantees which step comes next, what counts as done, or how to continue after a crash. Badger adds those guarantees and leaves the reasoning inside each step to the Agent. It turns Skills into a workflow package with declared steps, then runs the package through a single runtime that checks and records every step.

Skill 是 Agent 照着执行的 Markdown 方法说明，写起来简单、搬起来方便，但没有任何机制保证下一步做什么、怎样才算完成、崩溃后如何接着做。Badger 补上这些保证，同时把每一步内部的推理仍交给 Agent：它把 Skill 组合成声明了步骤的工作流软件包，再由唯一的运行时逐步检查并记录。

1.1 How Badger works1.1 Badger 如何工作

Build time: Creator构建期：Creator

An Agent and the badger CLI turn a goal and explicitly named source Skills into a reviewed workflow package. The Agent supplies the meaning. The CLI validates, hashes, and writes only after you confirm (§3).

Agent 与 badger CLI 一起，把目标和明确指定的源 Skill 变成经过审查的工作流软件包。含义由 Agent 提供；CLI 负责校验和计算哈希，并且只在你确认后写入（§3）。

Run time: WorkflowRuntime运行期：WorkflowRuntime

One runtime executes the package as a durable Run. It proposes one action at a time, a person, Agent, or script performs it, and the runtime accepts the result only after checking it (§4).

唯一的运行时把软件包作为持久化 Run 执行：每次只提出一个动作，由人、Agent 或脚本完成，运行时检查结果无误后才接受（§4）。

Only one thing passes between the two halves: the assembled package, its immutable snapshot, and their hashes. Neither half reads or writes the other's internal state.

两半之间只交接一样东西：组装好的软件包、它的不可变快照及其哈希。任何一方都不读写对方的内部状态。

The repository also holds the first pieces of a collaborative service around this kernel: the walking skeleton of its server, which signs people in, locally or through the organization's AI platform, audits every write, and reports its health (§5.4), and the shell of its web dashboard (§5.5).

仓库中还有围绕这一内核的协作服务的最初几部分：其 server 的最小可运行骨架，负责登录（本地登录，或通过组织的 AI 平台登录）、审计每一次写入并报告自身健康状况（§5.4），以及其 Web 仪表盘的外壳（§5.5）。

Planned (#24). The rest of that service: a web dashboard where field experts and engineers build workflows together, organization roles, a questionnaire stored as records, and a Badger MCP for Agents. None of it is built yet; §7 summarizes the design.

规划中（#24）。该服务的其余部分：领域专家和工程师一起构建工作流的 Web 仪表盘、组织角色、以记录形式保存的问卷，以及供 Agent 使用的 Badger MCP。这些都尚未实现，§7 概述了设计。

1.2 Three rules behind most of the design1.2 贯穿设计的三条规则

1 · Nothing is written without confirmation1 · 未经确认，不写任何东西

Commands that only inspect never write. The first write is init --confirm. After that, generating, recording lane results, assembling, approving, and publishing each need their own --confirm, and so does the distribution preview.

只做检查的命令从不写入。第一次写入是 init --confirm；此后生成、记录 lane 结果、组装、批准和发布都各自需要 --confirm，分发预览也一样。

2 · Only WorkflowRuntime moves a Run2 · 只有 WorkflowRuntime 能推进 Run

People, Agents, and scripts do the work and submit results. The runtime alone decides whether to accept a result and what happens next. Generated scripts only forward to it.

人、Agent 和脚本负责干活并提交结果；是否接受、下一步做什么，只由运行时决定。生成的脚本只是把请求转交给它。

3 · Evidence belongs to one hash3 · 证据只对一个哈希有效

Evaluation, review, and approval count only for the exact package hash they examined. Change any file and that evidence goes stale until you rerun it.

评估、审查和批准只对它们检查过的那个软件包哈希有效。改动任何文件，这些证据就会过期，必须重新执行。

1.3 When Badger fits1.3 什么时候适合用 Badger

Use Badger when the steps and what counts as done can be written down in advance, even if the work inside a step still needs an Agent, a tool, or a person. A plain Skill is enough when you need no guarantees. A general Agent runtime fits better when the route itself has to be invented while running.

如果步骤以及“怎样算完成”能事先写清楚——哪怕每一步内部仍需要 Agent、工具或人来完成——就适合用 Badger。如果不需要任何保证，普通 Skill 就够了；如果路线本身要在运行中临时规划，通用 Agent 运行时更合适。

SECTION 02第 02 节

The workflow contract工作流契约

A Badger workflow is declared, not improvised. The Workflow Protocol is normalized from the plan and stored in the package as reference/workflow-protocol.json. It names every Node, what each Node must prove, and which moves are legal. WorkflowRuntime executes only what the Protocol declares.

Badger 工作流是事先声明的，而不是临场发挥的。Workflow Protocol 由计划规范化而来，存放在软件包的 reference/workflow-protocol.json 中，列出每个 Node、每个 Node 需要证明什么，以及哪些流转合法。WorkflowRuntime 只执行 Protocol 声明的内容。

2.1 Nodes and their relationships2.1 Node 及其关系

These are the relationships a plan expresses. The questionnaire and the authoring lanes use the same terms (see also GLOSSARY.md).

以下是计划所表达的关系，问卷和创作 lane 使用同一套术语（另见 GLOSSARY.md）。

Node
One stage of the workflow, with its own responsibility, completion evidence, and outcomes. Its kind says why it exists: producer (produces artifacts and evidence), action (performs work), decision (asks the workflow owner), handoff (passes evidence on), guardrail (enforces a check), or control (routing structure).工作流中的一个阶段，有自己的职责、完成证据和可能的结果。kind 说明它为何存在：producer（产出产物与证据）、action（执行工作）、decision（询问工作流负责人）、handoff（传递证据）、guardrail（执行检查）或 control（路由结构）。
Implementation bindingImplementation binding（实现绑定）
The supplied Skill that owns a Node's work.负责这个 Node 工作的那个源 Skill。
Required Skill CallRequired Skill Call（必需 Skill 调用）
Another supplied Skill that must be called inside the Node. It does not replace the implementation.在该 Node 内必须调用的另一个源 Skill；它不取代实现绑定。
AugmentationAugmentation（增强）
A Skill that assists the Node without replacing its implementation. Enforced augmentations are checked; advisory ones never block.辅助该 Node 但不取代实现的 Skill。强制型增强会被检查，advisory 型永不阻塞。
Output Schema
What the Node must produce before it counts as done: declared artifacts, each with a kind, a bounded path, and a validation kind, plus evidence fields. An Agent saying “done” is not enough.Node 必须产出什么才算完成：声明的产物（各有类型、有界路径和校验方式）以及证据字段。Agent 说“做完了”不算数。
Guardrail
A check, based on declared validation or evidence, that must pass before the workflow advances.基于声明的校验或证据、推进前必须通过的检查。
Decision Node
A stable question for the workflow owner, with fixed choices. Each choice maps to a declared transition.向工作流负责人提出的固定问题和固定选项；每个选项对应一条声明的转换。
Handoff
Bounded evidence returned to another Node, a reviewer, or the user. It does not ask anyone to choose between outcomes.把有界证据交给另一个 Node、审查者或用户；它不要求对方在结果之间做选择。

A declared move after success, failure, or pause, or after a decision choice. A routing condition may test a declared value, such as scenario=pool-only.在 success、failure、pause 或某个决策选项之后的声明式流转。路由条件可以检查声明过的值，例如 scenario=pool-only。
Cycle
A declared region that may repeat. It has an entry Node, repeat transitions, and a finite maxInstances budget.可以重复的声明区域，有入口 Node、重复转换和有限的 maxInstances 预算。

2.2 What stays fixed and what stays flexible2.2 哪些固定，哪些灵活

  • Fixed: the graph of Nodes and transitions, what each Node must prove, and which decisions exist. Routing accepts only declared fields and values, using exact matches and at most one fallback. Ambiguous routes, undeclared values, undeclared loops, and unreachable required Nodes are rejected before any Run starts.
  • Flexible: how the work inside a Node gets done. A person, Agent, script, or tool may do it, and an Agent's reasoning may differ from run to run. Badger checks only the result.
  • 固定：Node 与转换构成的图、每个 Node 需要证明的内容，以及有哪些决策。路由只接受声明过的字段和值，采用精确匹配，最多一个回退分支；有歧义的路由、未声明的值、未声明的环和不可达的必需 Node，在任何 Run 开始前就会被拒绝。
  • 灵活：Node 内部的工作怎么完成。可以由人、Agent、脚本或工具完成，Agent 的推理每次可以不同，Badger 只检查结果。

Anything beyond a simple linear workflow is an opt-in capability: branches, decisions, Cycles, versioned artifacts, and durability options such as locks, journals, and checkpoints (§6.1). Turn one on only when the domain needs that extra proof.

简单线性工作流之外的功能都是可选的 capability：分支、决策、Cycle、产物版本，以及锁、日志、检查点等持久化选项（§6.1）。只有领域确实需要这层额外保证时才启用。

Build a package with Creator用 Creator 构建软件包

Creator takes a workflow from idea to published package in three phases: agree on meaning, author the content, then prove and release it. Every phase ends at a gate, and nothing passes a gate without a confirmation or current evidence.

3.2 Phase 1: agree on meaning3.2 第 1 阶段：确认含义

Sources are closed-world. Badger never searches for Skills. You declare each one by name and location in skillSources, and the source check, badger source-check (badger candidates is kept as an alias), inspects exactly those Skills, read-only. It reports each source's identity hash, an inventory of every file in that identity, configuration included, with its hash, the source's references and scripts, the files it ignored, and any blockers. Identity covers every file except a fixed, documented list of operating-system metadata, editor state, and interpreter caches (for example .DS_Store, .idea/, and __pycache__/). Those files stay out of both the hash and the inventory, so adding or removing one changes neither a proposal nor a package, and the source check lists them under ignored. A script's side effects (none, local-writes, network, scheduler-submission, installs) are declared in the source manifest or the plan's skillSources, and an undeclared script is reported as undeclared. A relative location must stay inside the project. An absolute location must stay inside the project or a root the host registers with --source-root or BADGER_SOURCE_ROOTS; a plan or a manifest cannot register roots itself. A missing, ambiguous, or out-of-scope source becomes a blocker; Badger never guesses.

来源是封闭的。Badger 从不自行查找 Skill：每个 Skill 都要在 skillSources 里以名称和位置声明，来源检查 badger source-check（badger candidates 保留为别名）只读地检查这些 Skill，报告每个来源的身份哈希、由构成身份的每个文件（包括配置）及其哈希组成的文件清单、该来源的参考资料与脚本、被忽略的文件，以及所有阻塞项。身份覆盖除一份固定且有文档记录的操作系统元数据、编辑器状态和解释器缓存清单（例如 .DS_Store、.idea/ 和 __pycache__/）之外的每个文件。这些文件既不计入哈希，也不进入文件清单，因此增删它们既不改变提案，也不改变软件包；来源检查把它们列在 ignored 下。脚本的副作用（none、local-writes、network、scheduler-submission、installs）在来源清单或计划的 skillSources 中声明；未声明的脚本会报告为未声明。相对位置必须留在项目内。绝对位置必须留在项目内，或宿主用 --source-root 或 BADGER_SOURCE_ROOTS 注册的根目录内；计划和来源清单都不能自行注册根目录。缺失、有歧义或超出范围的来源会成为阻塞项，Badger 从不猜测。

Library callers get these four operations from createWorkflowRuntime(protocol), and nothing else is public. 库调用方通过 createWorkflowRuntime(protocol) 获得这四个操作，其他都不公开。每次调用返回的 continuation 用 disposition 告诉宿主下一步：continue（有机器动作待处理）、await-user（去问工作流负责人）、blocked（需先修复，findings 会说明原因）或 done（结束）。

4.2 What submit checks4.2 submit 检查什么

A result changes nothing until it passes all of these checks:

结果必须全部通过以下检查，才会改变任何东西：

  • Identity. It must answer the current pending actionId. Decision answers, and every submission to a Run with durability features, must also quote the current revision, Run id, and execution identity. A mismatch is rejected and changes nothing, so a replayed submission can never advance the Run twice.
  • Completion. The Node's Output Schema artifacts and evidence, required Skill calls, enforced augmentations, and guardrails must all be satisfied. Proof of completed checks goes in evidence.completedChecks.
  • Artifacts. Each required versioned output names either one declared file update or one exact accepted version. Badger never picks “the latest file.”
  • Route. Routing values must be declared, and exactly one transition may match.
  • 身份。必须回答当前待处理动作的 actionId。决策回答，以及对启用了持久化能力的 Run 的所有提交，还必须注明当前的 revision、Run id 和执行身份。不一致的提交会被拒绝且不改变任何东西，所以重放的提交永远不会让 Run 前进两次。
  • 完成。该 Node 的 Output Schema 产物与证据、必需的 Skill 调用、强制型增强和 Guardrail 都必须满足；已完成检查的证明放在 evidence.completedChecks 中。
  • 产物。每个必需的版本化输出，要么指明一次声明过的文件更新，要么指明一个确切的已接受版本。Badger 从不自动选“最新的文件”。
  • 路由。路由值必须是声明过的，并且只能匹配到一条转换。

A missing prerequisite returns blocked with the same pending action, so you resubmit corrected evidence without redoing the work. A failed outcome (status: "failed") follows the Engine's retry policy, and the repair policy too if it is enabled.

缺少前置条件时返回 blocked，待处理动作保持不变，补齐证据后重新提交即可，无需重做工作。失败的结果（status: "failed"）按 Engine 的重试策略处理；若启用了修复策略，也按修复策略处理。

4.3 Decisions4.3 决策

A decision Node becomes a persisted ask_user action. Its await-user continuation carries the stable question and choices, the input schema, the rationale policy, and the reviewer requirement. Only submit can answer it, and the answer must match the revision, action, Node, Cycle, Attempt, package identity, choice, reviewer, inputs, rationale, and any required artifact or evidence references. An accepted answer creates one Decision Receipt and follows only the chosen transition. A stale, replayed, or mismatched answer changes nothing. If an artifact that the question refers to changes after the question is asked, the answer is stale too.

决策 Node 会变成持久化的 ask_user 动作，其 await-user continuation 包含固定的问题与选项、输入 Schema、理由要求和审查者要求。只有 submit 能回答它，回答必须与 revision、动作、Node、Cycle、Attempt、软件包身份、选项、审查者、输入、理由，以及所需的产物或证据引用全部一致。被接受的回答生成一张 Decision Receipt（决策回执），并且只沿所选的转换前进。过期、重放或不匹配的回答不会改变任何东西；如果问题所引用的产物在提问后发生了变化，回答同样作废。

4.4 Cycles, Attempts, and artifact versions4.4 Cycle、Attempt 与产物版本

Cycle
Each entry into a declared repeat region gets a stable Cycle identity, up to maxInstances. When the budget runs out, the Run blocks instead of looping.每次进入声明的重复区域，都会获得一个稳定的 Cycle 身份，最多 maxInstances 次；预算用完时 Run 进入阻塞，而不是无限循环。

One visit to a Node. Retries stay inside the same Attempt. Re-entering the Node, for example in a new Cycle, creates a new Attempt, so evidence from different visits never overwrites each other.对某个 Node 的一次访问。重试留在同一个 Attempt 内；重新进入该 Node（例如在新的 Cycle 中）会创建新的 Attempt，不同访问的证据互不覆盖。
Artifact versionArtifact version（产物版本）

4.5 Recovery and durability4.5 恢复与持久化

Every committed change goes through protected, bounded, atomic writes, and a failed write never replaces the last valid state. A workflow's durability profile can opt into stronger guarantees:

每次提交的变更都经过受保护、有边界的原子写入，写入失败绝不会覆盖最后一个有效状态。工作流的持久化配置还可以选择更强的保证：

  • Transition journal: a write-ahead record of the previous and intended files. While it is pending, resume and submit return recovery-required.
  • Mutation lock: one mutating operation per Run at a time. A lock is never stolen, and only recover may clear one whose owner process is proven gone. A lock names its host by a hashed identity of the boot and the process namespace, not by the hostname, so renaming the host keeps it attributable. An owner on another boot, namespace, or host, or one whose identity cannot be read, stays unknown, and recover refuses it too (#32, ADR 0018).
  • Verified checkpoints: content-addressed manifests written after each commit. Recovery falls back to an older checkpoint only when the history proves that nothing later was committed.
  • Also available: content snapshots of declared project files, verification receipts, a repair policy (a finite failure budget, then ask or stop), and transactional finalization (preview, confirm, apply, reconcile).
  • Transition journal（转换日志）：预写式记录变更前后的文件内容。日志未处理完时，resume 和 submit 返回 recovery-required。
  • Mutation lock（变更锁）：同一时刻每个 Run 只允许一个变更操作。锁从不被强占；只有 recover 能清除那些已证实持有进程不存在的锁。锁以开机实例与进程命名空间的哈希身份而非主机名标识所在主机，因此主机改名后归属依然可识别。持有者若属于另一次开机、另一个命名空间或另一台主机，或其身份无法读取，就保持未知，recover 同样拒绝接管（#32，ADR 0018）。
  • Verified checkpoints（验证检查点）：每次提交后写入内容寻址的清单；只有当历史证明之后没有任何提交时，恢复才会退回到较早的检查点。
  • 其他可选项：对声明的项目文件做内容快照、验证回执、修复策略（有限的失败预算，用完后询问或停止），以及事务式终结（预览、确认、执行、对账）。

recover works only from the persisted records, never from chat history or generated files. It rolls known interrupted writes forward, leaves unknown material untouched and blocked, and never repeats external work.

recover 只依据持久化记录工作，从不依赖聊天记录或生成的文件。它把已知的中断写入向前补完，不碰未知内容并保持阻塞，也从不重做外部工作。

6.5 Artifact receipts and external roots6.5 产物回执与外部根目录

Declarations and their limits

An Output Schema declares externalRoots as a map of names to {"description": "..."}, with at most 32 roots per schema and per workflow. A name has at most 128 characters; a nonempty description has at most 1,000 characters. Every root is used by an artifact in its schema, and a shared name has the same description everywhere. A declaration holds no directory or path. Describe what the directory holds, where it usually lives, and who owns it: the description becomes the Agent's question.

Artifacts opt in with verification: "receipt". Only then may they use root and requireCurrentAttempt, including an explicit false. An omitted root means the Run root. Paths are relative to the selected root, permit only * wildcards, and reject absolute paths, empty or dot segments, traversal, NUL, and ?. Receipt verification streams SHA-256 and can verify large artifacts; other artifacts stay inside the Run root under the 2 MiB content cap.

Binding and discovery

The kernel's startRequirements(protocol) is read-only and needs no Run. The script adapter's status before start forwards it as startRequirements. After the person chooses and confirms all directories, the kernel's externalRoots start option binds the map once for the Run. In the script adapter, use init --external-root <name>=<directory>, once per root. See the §4.6 procedure. The binding is fixed for that Run; no directory is guessed or reused from another Run without asking.

The continuation and next expose the current Node's receiptOutputs: artifactId, paths, root: {name, path}, and requireCurrentAttempt. A null root name identifies the Run root. Recovery in a fresh process returns the same bound directories.

Receipts, freshness, and findings

Accepted Completion evidence stores evidence.artifactReceipts. Each receipt has artifactId; root: {name, path} for an external root (omitted for the Run root); absolute path; byte size; sha256; modification time mtimeMs; and producer, which contains runId, nodeId, cycleId, attemptId, actionId, and revision. Directory receipts hash a manifest of file hashes and directory entries, and their size sums the files.

There are at most 256 receipts per Completion and 256 entries per directory receipt, including the directory being verified. Each file is checked for freshness; an empty directory uses its own modification time. With requireCurrentAttempt: true, modification time must be at or after the Attempt's first persisted action. Retrying keeps that boundary; re-entering the Node starts a new Attempt. Copies that preserve old timestamps (cp -p, rsync -a) or a filesystem clock behind the host can make newly copied output appear stale: write outputs afresh during the Attempt.

  • artifact-stale-attempt: Workflow artifact <schema>.<artifact> is stale for this Attempt: <relativePath>. A carried version from another Attempt is stale too.
  • artifact-content-drift: Workflow artifact content drift detected: <versionId>. A stored version's current content no longer matches its receipt.
  • external-root-binding-required: a start binding is missing or invalid. The finding has requiredAction: "execute", operation workflow.start, and requiresUserDecision: true. Ask the person, confirm their directories, and start again.

Receipt verification refuses changes during a read (Workflow artifact <schema>.<artifact> changed during receipt verification), unsafe traversal, symbolic links, junctions, and special filesystem objects. Limits refuse with Output Schema artifacts exceed 256 receipts per Completion or Workflow artifact <schema>.<artifact> exceeds 256 receipt entries. A capture failure is wrapped as Workflow artifact <schema>.<artifact> receipt verification failed: <reason>.

What verification never does

Verification never copies, writes, or publishes a file; it grants no access beyond the declared paths and never attests which process wrote a file. A receipt records content identity and freshness evidence, not process provenance.

声明及其限制

Output Schema 通过 externalRoots 声明名称到 {"description": "..."} 的映射。每个 schema 和整个工作流最多各 32 个根目录；名称最多 128 个字符，非空说明最多 1,000 个字符。每个根目录必须被所属 schema 的产物使用，共享名称在各处的说明必须相同。声明不包含目录或路径。说明应交代目录存放什么、通常位于何处、归谁所有，因为它会成为 Agent 向运行者提出的问题。

产物通过 verification: "receipt" 启用回执验证，只有此时才能设置 root 与 requireCurrentAttempt，即便后者显式为 false 也一样。未指定根目录时使用 Run 根目录。路径相对于所选根目录，只允许 * 通配符，拒绝绝对路径、空或点路径段、越界、NUL 和 ?。回执验证以流式 SHA-256 校验大型产物；其他产物仍限于 Run 根目录并受 2 MiB 内容上限约束。

Evaluation runs as a sandboxed worker job, and every report is kept with its package hash.

Agent 起草，人来签字。接入的 Agent 通过作业完成起草：源文件研读、问题与追问、重述与翻译、档案和计划的草稿、按 Wave 顺序进行的创作 lane，以及审查投票。每个作业都带有绑定哈希的上下文包、输出 Schema 和租约；租约过期后作业回到队列，输入变化则作业取消。作业结果只是草稿，只有经人接受，才能进入记录、档案、计划或软件包。评估作为沙箱中的 worker 作业运行，每份报告都连同其软件包哈希保留下来。

7.4 The questionnaire as records7.4 以记录形式保存的问卷

The questionnaire of §3.2 moves out of the chat and into records, one questionnaire per workflow version. The Engineer drafts questions, each with a topic, targets, a rationale, evidence links into a Skill version, assignees, and a priority, and publishes them in rounds. A round has no size limit unless the workflow sets one. Experts answer from My work in any language, with drafts saved as they type and every revision kept, and may raise concerns that nobody asked about. Rounds, free-text answers, revisions, resolutions, expert acknowledgements, threads, and concerns already work this way (§5.4, §5.5); ledger composition and readiness are to follow.

§3.2 的问卷将从对话中移出，变成记录，每个工作流版本一份。工程师起草问题——每个问题有主题、对象、理由、指向某个 Skill 版本的证据链接、指派人和优先级——并按轮次发布。除非工作流另行设定，一轮问题没有数量上限。专家在“我的工作”页面作答，可以使用任何语言，草稿随输入自动保存，每个修订都会保留；专家也可以主动提出没人问到的关切。轮次、自由文本回答、修订、处理结论、专家认可、讨论串与关切已按此方式工作（§5.4、§5.5）；账目编制与就绪检查将随后提供。

Confirming an answer restates it as one or more facts in the workflow's locale, linked to the answer revisions it came from. The expert who answered acknowledges or disputes each restatement, and a dispute reopens the question. A deferral needs a reason: a question internal to one Skill moves to that Skill's backlog, and deferred questions never block the dossier. Agent inferences stay drafts until a confirming question settles them.

确认一个回答，就是把它重述为工作流语言区域下的一条或多条事实，并链接到其来源的回答修订。作答的专家认可或质疑每条重述，质疑会让问题重新打开。延后必须给出理由：只涉及某个 Skill 内部的问题转入该 Skill 的待办，延后的问题从不阻塞档案。Agent 的推断在被某个确认性问题解决之前，一直只是草稿。

The five ledgers of §3.2 become read models over these records, so they survive sessions and can show what changed since any round. Readiness is computed per dossier topic, including interfaces, and names its blockers: unresolved questions, unconfirmed inferences, unresolved assumptions, pending acknowledgements, and disputes. Composing a dossier snapshots the ledger as canonical JSON with its hash, in the version 2 schema of §3.2. A new workflow version copies the facts and resolutions and reopens only those whose evidence changed.

§3.2 的五类账目变成基于这些记录的读模型，因此不会随会话结束而丢失，并且可以显示自任意一轮以来的变化。就绪检查按档案主题（包括接口）计算，并列出阻塞项：未解决的问题、未确认的推断、未解决的假设、待认可的重述，以及质疑。编制档案会按 §3.2 所述的 Schema 第 2 版，把账目快照为规范化 JSON 及其哈希。新的工作流版本会复制已有的事实和处理结论，只重新打开证据有变的那些。

7.6 Notifications7.6 通知

Everyone gets an in-app inbox, whose items close by themselves when the thing they announce is done, such as a question answered or a gate closed. The inbox already carries the Sources gate's items and assigned questions, which close once answered (§5.5); the other items are to arrive with their records. In the first version the worker also posts in each workflow team's WeCom group chat through a group robot, whether the action happened in the dashboard, through the Badger MCP, or in a Run.

每个人都有应用内收件箱；条目所通知的事项完成后（例如问题已回答、门槛已关闭），条目会自动关闭。收件箱已承载“来源”门槛的条目和指派的问题，问题回答后条目自动关闭（§5.5）；其他条目将随各自的记录一起到来。第一版中，worker 还会通过群机器人在每个工作流团队的企业微信群里发消息，无论操作发生在仪表盘、Badger MCP 还是 Run 中。

  • Setup. A Workflow owner pastes the robot's webhook URL and picks the chat's language; a Group lead may set a default robot for the group's workflows. Saving sends a test post. Anyone holding the URL can post to the chat, so it is stored encrypted, shown masked, and never logged.
  • Posts. One post per action per chat, @mentioning each recipient by WeCom userid or mobile number. A post carries only the workflow's name, what is waiting, the counts, and a link. It never carries answers, Skill content, or Run artifacts, because every member of the chat sees it.
  • Delivery. Posts are paced to the robot's rate limit, retried with backoff, and recorded in a delivery log. A failed channel never blocks a gate, because the in-app item stands.
  • Remind. The person who requested an item, the Workflow owner, or an Administrator can nudge whoever it waits on, at most once per item per hour. Without a robot, Remind offers ready-to-paste text instead.
  • 设置。工作流负责人粘贴群机器人的 webhook URL，并选择该群的语言；组长可以为组内工作流设置默认机器人。保存时会发送一条测试消息。拿到这个 URL 的人都能往群里发消息，所以它加密存储、遮蔽显示，且从不写入日志。
  • 消息。每个操作在每个群只发一条消息，按企业微信 userid 或手机号 @ 每位接收人。消息只包含工作流名称、等待处理的事项、数量和链接，从不包含回答、Skill 内容或 Run 产物，因为群里每个成员都能看到。
  • 投递。消息按机器人的频率限制排队发送，失败时退避重试，并记入投递日志。渠道失败从不阻塞门槛，因为应用内条目依然有效。
  • 提醒。事项的发起人、工作流负责人或管理员可以提醒被等待的人，每个事项每小时最多一次。没有机器人时，“提醒”改为提供可直接粘贴的文字。

WeCom app messages to individuals, email, and the webhook bots of other chat tools come later, through the same notification port.

发给个人的企业微信应用消息、电子邮件，以及其他聊天工具的 webhook 机器人，将来都通过同一个通知端口接入。
